Gazpacho design review 1

I went back through design draft 1 looking for what is wrong, missing or too optimistic. The findings are first. Below them are nine decisions for you, each with my recommendation and its cost, and a list of points I intend to treat as settled. Press "Copy answers" and paste the result back to me.

What the review found

#FindingWeightHandled by
1The tree could be far simpler for a first version. With one member per leaf and fixed upper levels, the tree needs no shrinking-timelock layers at all. Exits are fast and almost no group signing happens after creation. The cost is that the host's spare liquidity is fixed per member.LargeQuestion 1
2A new member cannot pay for their own exit. Members start with nothing on chain, but a forced exit needs on-chain fees. Draft 1 did not say where those come from.LargeQuestion 2
3"Watching while the app runs" does not protect a member who is away. If the host publishes an old channel state, the member has a limited time to answer.LargeQuestion 3
4The channel's on-chain format was left unsaid. The old code's payment scripts have known flaws. Lightning now has a finished taproot channel format.LargeQuestion 4
5How members gather was not designed. Creating a factory needs every member online at once. There has to be a waiting room and a start time.MediumQuestion 5
6Receiving through the host's regular node needs a specific node feature. The member must keep the payment secret until the money is locked in their channel. The host's node has to be able to hold a payment open meanwhile.MediumQuestion 6
7A restored backup is dangerous. Publishing from an old copy looks like cheating and loses funds. Draft 1 described backup but not safe recovery.MediumSettled list
8Signing secrets must never be saved. "Save before send" does not apply to them. A signing round interrupted by a crash is abandoned and restarted with fresh ones.MediumSettled list
9The browser needs secure connections. A web page can only connect to a host that has a web certificate. Community hosts would each need one.MediumQuestion 8
10The "one safety rule" was oversold. It is the right principle, but working out "what can I leave with" covers timelocks, in-flight payments and fees. It needs its own precise definition and its own tests.MediumSettled list
11The "same transaction IDs" test proves little. We import the tree code unchanged, so it would match by construction. It is replaced by recorded reference results that catch drift when the import is updated.SmallFixed in the design
12Checking block headers is harder on signet. Signet blocks are signed, not mined in the usual way. On signet we compare several servers; the full check is for testnet and mainnet.SmallFixed in the design
13Missing pieces: a lifecycle manager for joining, rotating and closing, and the swap-in flow were not among the five engines.SmallFixed in the design
14The estimate was optimistic. Building the channel on Lightning's standard format is more work than draft 1 allowed. A first release is more likely 13 to 15 weeks than 11 to 12.MediumQuestion 9

Decisions for you

Points I will treat as settled

Object to any of these in the box.

  • Message format: speak Lightning's own wire language and carry factory messages inside one custom message type. No private format.
  • Foundations: imported as a pinned copy inside our repo. Changes go to the SuperScalar repo first.
  • Changes to the tree builder (such as paying members at every output on expiry): requested from the SuperScalar repo, not patched privately.
  • Safe recovery: an app restored from backup never publishes its own copy of a channel. It asks the host for proof of the latest state and waits for the host to close.
  • Signing secrets: never written to storage. An interrupted signing round is abandoned.
  • Backup location: an encrypted copy held by the host using Lightning's standard peer-storage messages, plus a file the user can export.
  • The safety rule: written as a precise definition with its own test suite before any engine uses it.
  • Sign before fund, save before send, and deadlines derived from exit time, as in draft 1.
  • Signet lifetimes: factories on our signet host live about a week, so testers see a rotation. Real lifetimes are a setting.
