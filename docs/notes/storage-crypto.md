# Storage encryption: the Slice 1 code

What `ports/storage/crypto/` builds from `spec/storage-encryption.md` draft 3, what it relies on, how it is tested, and the choices made where the specification is silent. Written 2026-11-12 with the first pull request of stream S6.

## Memory

Every storage-layer secret (the passphrase and its NFC copy, PK, MSK, every subkey and HKDF intermediate, the seed copy, the words' entropy) is in `sodium_malloc` memory and freed with `sodium_free`, which wipes it. That includes the exports, which 8.3 does not name (review A, M2; a gap for the next draft): an opened export body may hold the words' entropy, so `gz_sc_export_open` gives it in `sodium_malloc` memory, to be freed with `gz_sc_sfree`; and the words never pass through the builder's buffer, which in practice holds the whole journal in ordinary heap: the caller builds the body without them (flag bit 0 set) and hands the 32 bytes, in guarded memory, to `gz_sc_export_build`, which puts each chunk that carries them together in guarded memory before sealing it. The generated passphrase is drawn and joined in constant time: every word of the list is read for each of the six, and each output byte reads every slot, so no memory index depends on the secret word (`storage_ctime` runs it with the random source marked secret). The masks pass through an empty `asm` value barrier: without it, gcc at `-O2` turned the masked join back into branches and folded a secret offset into a loop's induction variable, which `storage_ctime` reported at once; with it the test is clean with gcc and clang 18 at `-O0`, `-O1`, `-O2`, `-O3` and `-Os`, with and without `-g`. Long-lived keys (the vault's MSK and seed, key pairs) are `sodium_mprotect_noaccess` between uses. The helper locks its pages with `mlockall(MCL_CURRENT | MCL_FUTURE)` only when `RLIMIT_MEMLOCK` (raised to its hard limit) covers the derivation plus 64 MiB: with `MCL_FUTURE` and a smaller limit, Argon2's allocation would fail, and 8.3 says a refused lock must not stop the derivation. It reports whether it locked (`mem_locked`), for 14's "memory not locked". The storage layer is single-threaded: the `mprotect` toggles are not safe across threads.

- **The passphrase blocklist** (spec open point 3, decided by the coordinator on the owner's behalf on 2026-11-12, open to the owner's change): the most common million of Mark Burnett's "10 million passwords" (2015, which he placed in the public domain), as published in SecLists (MIT licence, copyright Daniel Miessler; the notice is kept in `sc_blocklist.c`), `Passwords/Common-Credentials/xato-net-10-million-passwords-1000000.txt` at commit `dbfb830d95e4f3da4fb7d7d277ed597de0ed7a18`, SHA-256 `424a3e03a17df0a2bc2b3ca749d81b04e79d59cb7aeec8876a5a3f308d0caf51`. It is the corpus zxcvbn's password list comes from. `tools/gen-blocklist.py` refuses any other file and keeps only the entries that can ever match: 4.1 refuses fewer than 15 code points before the list is consulted, every line of the file is ASCII, and an ASCII entry shorter than 15 characters can never equal the case-folded form of a passphrase of 15 code points or more. That leaves 10,898 distinct entries (of the million; 3 lines, empty or with control characters, are skipped), lowercased, sorted for a binary search (225 KB of strings). The top 100,000 would have left 70, too few to matter, so the million was taken. Matched whole after NFC and case folding, as 4.1 says. It catches "passwordpassword", "qwertyuiopasdfg" or "1234567890123456"; it does not catch "password1234567", which is not in the million: a list cannot be the only defence, which is why the generated passphrase is offered first (14). The tests check the digest of the kept entries, their order and form, and that entries across the list are refused.
- **The EFF large word list** (7,776 words), https://www.eff.org/files/2016/07/18/eff_large_wordlist.txt, SHA-256 `addd35536511597a02fa0a9ff1e5284677b8883b83e986e43f15a3db996b903e`, licence CC BY 3.0 US (attribution in `sc_wordlist.c`). Not the BIP 39 list. `tools/gen-eff-wordlist.py` generates `sc_wordlist.c` and refuses any other file; the tests check a digest of the words.

## Choices where the specification is silent

Each is a choice made here, open to the next review of the specification.

1. **The helper's page lock** (8.4). The specification says to raise `RLIMIT_MEMLOCK` and call `mlockall(MCL_CURRENT | MCL_FUTURE)`. With the usual limit of a few MiB, `MCL_FUTURE` makes Argon2's later 256 MiB allocation fail, which would turn "memory not locked" into "could not be checked". The helper locks only when the limit (raised to the hard limit) covers the derivation plus 64 MiB, and otherwise runs unlocked and says so. On the build server the limit is small: `mem_locked` is 0 there. **Specification gap**: 8.4 should say this.
2. **The helper's request format** is not specified: here `"GZKDFRQ1"`, t, m, salt, passphrase length, passphrase; the answer is a status byte (0 ok, 1 parameters refused, 2 failed), a locked byte and PK. The helper checks the parameter rule itself (release floor). A helper that exits non-zero, answers short or answers an unknown status is "could not be checked".
3. **Physical memory unknown** (4.2's third ceiling): the other two ceilings still apply; the device bound is skipped rather than refusing every file.
4. **A new wrap on a small device** (4.7, 11 "bounded by the exporting device's ceiling"): the memory is halved until the device allows it, never below the stored value or the floor; passes are never lowered.
5. **The attempts delays** (`local-api.md` 4.3, D15): one attempt a second whatever the result; after the fifth wrong one in a row the wait is 2, 4, 8 … seconds, at most 900. The strictest state (12.3) is `blocked_until = now + 900`, wrong count 0, and the counter read from the damaged file when its length is right, so it does not fall. A mode 2 file, which Slice 1 cannot check without KB, is read as damaged. **No file can impose more than the strictest state** (review A, L1, probe P1): mode 1's check is unkeyed, so whoever can write the folder can write a valid file; that writer is outside what 12.3 defends, but capping costs nothing, so a valid file's `blocked_until_s` is cut to now + 900 and its `last_wrong_s` to now. The counter saturates at 2^64 − 1 instead of wrapping to 0 (probe P1b), and the times saturate too. **Specification gap**: 12.3 should bound the strictest state a forged or replayed file can impose.
6. **The passphrase rules** (4.1). "The wallet's name with or without digits": both are case-folded (utf8proc) and compared with every ASCII digit and space removed, so "Holiday Fund 2026" against a wallet named "Holiday Fund" is refused and "Holiday Fund 2026!" is not. "Three or more of the wallet's own 24 words in order": the case-folded passphrase is split into runs of ASCII letters, and three of them matching words of the mnemonic at increasing positions (not necessarily adjacent) refuse it. Blocklist entries are compared whole after case folding.
7. **The bundled blocklist** (open point 3): decided on the owner's behalf and recorded under "Dependencies" above and in the specification's open point 3. Before review A the list was empty. "Fullwidth" spellings (`Ｇａｚｐａｃｈｏ 123456789`) pass the name rule, which case-folds but does not apply compatibility folding (NFKC would change what the person typed); accepted, the blocklist and the generated passphrase are the real defence.
8. **Export bodies**: flag bits other than bit 0 are refused; profile 2 with bit 0 is refused when built and when opened. The opener allocates up to the file's size, in guarded memory; the caller bounds the file size (the specification sets no export size limit; **gap**). A chunk length below 40 or above 65,576 is **damaged**, since no writer makes one; a chunk that runs past the end of the file is **truncated** (review A, L8; before, both were "truncated").
9. **The mark file** accepts equal consecutive points (a repeated append after a crash); only a decrease is damage. **The torn tail** is at most one invalid full entry, or a piece shorter than 56 bytes, after the newest valid entry: one append of 56 bytes can tear one entry, never two, so a second invalid full entry there is **damaged** (review A, L2, probe P2), never cut silently (7 rule 6). **Specification gap**: 10.2 should say "one". **The start rule** applies step 1 (possibly old) before step 2 (behind), so a missing guard with a mark file naming another journal reports "possibly old".
10. **Step 0** (6.3) writes a new journal header and mark file and leaves `guard.gzg` as it is; the restore's first batch (the core's `guard` record) rewrites it through `gz_sc_guard_write`.
11. **The socket token folder** (12.2): the data folder path is hashed as given (it must be absolute; symbolic links in it are not resolved); `XDG_RUNTIME_DIR` that is empty or relative counts as unset.
12. **libsodium is pinned exactly**: `gz_sc_init` refuses any version but 1.0.22 (the specification says 1.0.21 or later; the pin makes the build reproducible and the vectors' confirmation exact).
13. **Key commitment test** (16 test 5): built by giving a key file the commitment of passphrase A over a wrap sealed for passphrase B, which is what the commitment check has to stop; a true multi-key Poly1305 collision (Len, Grubbs, Ristenpart) is not constructed.
14. **E12, E13p, E14 (keyed)**: their files are 1.0.0's; the tests reproduce them from the same primitives and framing, so their bytes are confirmed with libsodium, but no product code reads them yet. **E15**: only the digest of the given canonical bytes is checked; the canonical JSON is the local API's (stream S9).
15. **POSIX only**: Linux is built and tested; the macOS branches (`getentropy`, `F_FULLFSYNC`, `confstr(_CS_DARWIN_USER_TEMP_DIR)`) are written but never compiled in CI; Windows (8.5) is not written.
16. **Core dumps of the main process** (8.3's `setrlimit(RLIMIT_CORE, 0)`, `PR_SET_DUMPABLE`, `MADV_DONTDUMP`) belong to the program's start, which does not exist yet (stream S11); the helper does its own.
17. **A storage fault is never "possibly old"** (review A, M1, probes P3 and P4). Only a file that does not exist (`ENOENT`) is missing. Any other failure to read the mark or the guard file (EIO, EMFILE, EACCES, a short read's error) makes `gz_sc_check_start` return `GZ_SC_STORAGE_FAILED`, and out of memory `GZ_SC_NOMEM`, with no outcome: 8.2 step 3 answers "storage fails" with a retry, while "possibly old" offers to start as a restore, which a transient error must never do to a sound wallet. The unlock's journal header read already returned its error, and a journal cut to fewer than 185 bytes is "not a file of this kind" (probe P9), never a missing journal. **Specification gap**: 8.2 step 3 and 6.3 should say this.
18. **The KDF helper's deadline** (review A, L3, probe P5): the parent waits for the answer with `poll` and reaps with `waitpid(WNOHANG)` against one deadline, 30 s plus 1 ms per 64 KiB pass (42 s at 256 MiB × 3, about 18 minutes at the 4 GiB × 16 ceiling, so a device at a sixteenth of a desktop's Argon2 speed still finishes); past it the helper is killed (`SIGKILL`), reaped, and the answer is "could not be checked". A helper that answers and then never exits is treated the same way. A program that sets `SIGCHLD` to `SIG_IGN` makes every derivation fail ("could not be checked", probe P6): safe, and a line for stream S11, which writes the program's start. **Specification gap**: 8.4 should state a timeout.
19. **`close_range`** is Linux 5.9 and later: on failure the child falls back to closing every descriptor in a loop, so the program's descriptors never reach the helper (review A, L8).
20. **The helper's page lock and `CAP_IPC_LOCK`** (review A, L8, optional): not changed. A process with the capability (a service run as root) could lock beyond `RLIMIT_MEMLOCK`, but `mlockall(MCL_CURRENT | MCL_FUTURE)` in a sanitizer build locks its shadow mappings too (terabytes of reserved address space), which on the build server, where the tests run as root, would exhaust memory; the rule stays "lock only when the limit covers the derivation", and a service that wants locking raises its limit.
21. **Costs left as they are** (review A, L8): the parameter upgrade derives the old PK again (with the unlock's, a third Argon2id where 4.7 counts two; once per upgrade, noted in `gz_storage_files.h`); `gz_sc_anchor` reads and opens the whole mark file at each anchored batch (5.6 MB and 100,000 opens after 100,000 anchored batches). Keeping the newest point in `gz_sc_unlocked_t` needs a file-size call in the OS table to notice a file changed underneath, and the single-writer rule written down; it belongs with open point 16 (the cost of anchored batches, to be measured with the journal).
22. **Stale temporary files**: a `name.tmp` left by a crashed replace is sealed but useless; `gz_sc_unlock` removes the five possible ones once the key file has opened (a wrong passphrase changes nothing on disk), and the next replace of a file removes its own as before (review A, L8).
23. **Local side channels below 8.3's line** (review A, L5): `gz_sc_pass_nfc`, which every caller runs on every unlock, and the refusal rules branch on the passphrase inside utf8proc; a co-resident process timing the cache could learn something of the passphrase while it is typed in. That is below 8.3's "a same-user attacker while unlocked", which is not defended; the generated passphrase, which the program makes and shows, is drawn in constant time (above). `storage_ctime` does not run NFC.

## Review A (PR 25) and the specification's next draft

Reviewer A's findings on the first commit of PR 25 and where each is answered: M1 (choice 17), M2 ("Memory"), M3 (the passphrase row of "What is built", `gz_storage_files.h`), L1 (choice 5), L2 (choice 9), L3 (choice 18), L4 (`ci.md`, "libsodium and utf8proc in every job"), L5 (`storage_ctime`, choice 23), L6 (`gz_sc_check`), L7 (the tests above; the mutation section), L8 (choices 7, 8, 19 to 22, and utf8proc under "Dependencies"). Points for the specification's next draft, from that review: 10.2 should say that one trailing invalid entry at most is a torn tail; 8.2 step 3 and 6.3 that a read error of the guard or mark file is a storage failure, not "possibly old"; 8.4 the helper's page-lock condition (choice 1) and a timeout; 12.3 the strictest state a forged or replayed mode 1 file can impose; 8.3 the export body as a place the words pass through.
