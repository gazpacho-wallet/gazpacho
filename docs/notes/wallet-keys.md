# Wallet keys: notes for later

Written 2026-11-11 after the independent review of pull request 6 (`wallet-keys`). It records what the key library and the `gz-wallet-keys` tool promise, what they do not, and what the next pieces of the on-chain wallet will need from them. The interface itself is documented in `wallet/include/gazpacho/wallet_keys.h`.

## 1. What the self-checks prove, and what they do not

The library and the tool check their own results in five places. The reviewer judged two of them real, one partly independent and one weak. That judgement is recorded here so nobody leans on a check for more than it gives.

| Check | Where | What it proves | What it does not prove |
|---|---|---|---|
| The signing key pair's public key equals the output key computed from the public key alone | `gzw_taproot_tweak_seckey`, `gzw_bip86_tweaked_keypair` | **Real.** The private route (negate if odd, add the tweak to the secret key) and the public route (add the tweak to the point) are different computations. If they agree, the key that will sign is the key the address pays to | That the tweak itself is the right one: both routes use the same tweak value. The BIP 86 and BIP 341 vectors cover that |
| The phrase file is read back from disk and the address derived again before anything is printed | `gz-wallet-keys new` | **Real.** What is on disk is what the address came from. A short write, a wrong file or a damaged phrase is caught | Nothing about the derivation: both derivations use the same code |
| Each output is derived twice: privately down to the leaf, and publicly below the account key | `gzw_bip86_output_from_master` | **Partly independent.** The last two steps use different arithmetic (scalar addition against point addition), so a slip in one of them shows | The three hardened account steps, the HMAC, the path and everything after the key (tweak, script, address) are shared by both routes. A wrong purpose, coin type or tweak passes this check. The vectors and the cross-check against other implementations are what cover those |
| An address is decoded again and compared with the key | `gzw_p2tr_address` | **Weak.** The decoder shares the checksum arithmetic, the character table and the prefix table with the encoder, so a mistake in any of them cancels out. It catches only an encoder that writes something the decoder cannot read back | That the address is right. The BIP 350 and BIP 86 address vectors prove that |
| A new phrase is decoded again and compared with the entropy | `gzw_phrase_from_entropy` | Our encoder and the imported decoder agree, and they are different code | That either is BIP 39. The 24 official vectors prove that |

`secp256k1_xonly_pubkey_tweak_add_check` in `gzw_taproot_output_key` repeats the same relation in the same library; it guards against a slip in our calls and nothing else. Removing it, the phrase read-back comparison, or the tool's address comparison changes no test result, because each is a second line behind a check that the tests do exercise. They are kept as cheap insurance and are not counted as tested protections.

What gives real assurance that an address can be spent: the official vectors (162, generated by script from the published files), the differential cross-check against embit and buidl (`wallet/tests/crosscheck.py`, run by hand because it needs third-party packages), the reviewer's 12,000-case differential run, and the signing test that verifies a BIP 340 signature against the key decoded from the address text.

## 2. Failure handling a wallet must build on

- **Reason codes.** The derivation functions report why they failed through `gzw_reason`. `GZW_REASON_INVALID_CHILD` is BIP 32's rare case (about 1 in 2^127). The library never skips an index by itself. A wallet that asks for index *i* and gets this reason must use *i*+1 and treat *i* as permanently unused, as every implementation that follows BIP 32 does. If *i*+1 fails too, the invalid step is in the account part of the path. For `gzw_bip32_master` the same reason means the seed has no master key. The cases are forced in `wallet/tests/test_wallet_rare.c` by replacing HMAC at link time.
- **Bad argument and invalid key are different.** `GZW_REASON_BAD_ARGUMENT` and `GZW_REASON_INVALID_KEY` are the caller's mistakes and must not be answered by trying the next index.
- **Overlapping arguments.** An output may be the same object as an input only where the header says so. Where it is allowed and the call fails, the shared object is zeroed and the input is lost.
- **Networks are an enum, not a flag.** `GZW_NET_MAINNET` is 0. The key-text functions take a `gzw_network`; the parse functions return a yes/no `is_mainnet` flag because the text does not say which test network a key belongs to.

## 3. Timing that depends on secrets

Two places take time that depends on secret data. Both matter only to someone who can measure this process closely on the same machine; neither is reachable over a network today.

- **Base58 in `wallet/src/bip32.c`.** Encoding and decoding an extended private key uses division and loops whose length depends on the value. It runs only when an `xprv`/`tprv` is written or parsed, which the tool never does.
- **The imported word search in `core/superscalar/src/bip39.c`.** Each word of a phrase is found by binary search with `strcmp`, so the time depends on the word. It runs whenever a phrase is checked or turned into a seed.

If the wallet is ever run where other parties share the machine, or a phrase is checked on behalf of a remote party, these two need constant-time replacements (the second one upstream).

Everything else that touches secrets goes through libsecp256k1's constant-time scalar and point routines and libcrypto's HMAC, SHA-256 and PBKDF2. `gzw_ct_equal` is used where the library compares secret-derived bytes.

## 4. RIPEMD-160 comes from the OpenSSL provider

Key fingerprints (in `xpub`/`xprv` text) need RIPEMD-160. The library takes it from libcrypto through `EVP_ripemd160()`. In OpenSSL 3.0.0 to 3.0.6 that digest lives only in the legacy provider, which is not loaded by default; from 3.0.7 it is in the default provider. Where it is missing, every child derivation fails cleanly with `GZW_REASON_INTERNAL` and no address is produced; nothing wrong is produced. CI (Ubuntu 24.04, OpenSSL 3.0.13) and the build server (3.5.5) both have it. A port to a platform whose libcrypto lacks it needs a small RIPEMD-160 of our own, tested by the BIP 32 vectors, which check the fingerprints.

## 5. Memory

- **No memory locking.** Neither the library nor the tool calls `mlock`. Secrets can be written to swap. The tool switches core dumps off before it reads anything.
- **Wiping.** Private keys, seeds, phrases and intermediate hashes are wiped before each function returns, and so are the public intermediates (account and leaf public keys) for consistency. Wiping of local temporaries cannot be shown by a black-box test; the reviewer checked it by scanning dead stack memory (`residue.c` in the review's scratch directory). What the tests do show is that every output is zeroed on failure.
- **The imported BIP 39 code** copies the PBKDF2 salt to the heap and wipes it before freeing. Its `bip39_entropy_to_mnemonic` frees an unwiped copy of the entropy; the wallet library does not call it.

## 6. No I/O: how the rule is enforced and its exceptions

`wallet/tests/check_no_io.py` holds an allow-list of every symbol the wallet objects may reference. Anything else fails the test, including fortified names such as `__fprintf_chk`. Five small bad libraries (a file write, a clock read, a print, a random read, a global counter) must each be rejected.

The same list is applied to the imported objects the wallet library pulls into a program, today `bip39.c` and `util.c`, with these exceptions, all in code that is imported unchanged:

| Symbols | Why they are there |
|---|---|
| `fopen`, `fread`, `fclose` | `bip39_generate()` reads `/dev/urandom`. The wallet library never calls it, but it is in the same object as the functions it does call |
| `malloc`, `free`, `realloc` | The PBKDF2 salt in `bip39_mnemonic_to_seed` (reached from `gzw_phrase_to_seed`); the `tx_buf` helpers in `util.c` (not called) |
| `PKCS5_PBKDF2_HMAC`, the `EVP_*` digest calls | BIP 39 seed stretching and SHA-256 through libcrypto |
| Writable data: `bip39_wordlist_en`, `secure_memset_ptr` | The word list is declared as an array of non-const pointers; the second is a volatile pointer to `memset` that keeps the compiler from dropping a wipe |

So the statement "the core never touches storage or randomness" holds for the wallet library's own code and for every imported function it calls, and does not hold for one imported function that is linked in but never called. Removing that needs a change upstream (move `bip39_generate` out of `bip39.c`) or building the imported files with one section per function and dropping unused sections at link time, which is a change to the shared top-level build.

## 7. Test networks share everything

testnet, testnet4 and signet use the same address prefix (`tb`), the same coin type (1) and the same extended-key version bytes (`tpub`/`tprv`). The same phrase therefore gives the same addresses and the same account key on all three, and an address does not say which of them it belongs to. regtest differs only in the prefix (`bcrt`). Consequences:

- Coins sent on one of these networks to an address shown for another are not lost, but the wallet will look for them on the wrong chain. The chain view must be told the network; the address cannot tell it.
- `GZW_NET_TESTNET4` is kept as a separate value so that later differences (a genesis hash, a default server list) have somewhere to live.
- Mainnet differs in all three respects, and the tool refuses it.

## 8. The tool's file handling

`gz-wallet-keys new` writes the phrase to `FILE.tmp-<random>` (created exclusively, mode 0600 from the first moment), syncs it, reads it back, links it to `FILE` (which fails if `FILE` exists), removes the temporary name, syncs the directory, and only then prints the address.

- A crash or kill before the link leaves no `FILE`. It may leave a `FILE.tmp-*` file, which can hold a phrase that was never used; delete it.
- Exit status 3 means the file was written and synced but the address could not be written to standard output. The file is kept; `address` shows the address.
- Hard links are needed. On a file system without them (FAT, some network mounts) `new` fails and creates nothing.
- Reading a phrase file refuses symbolic links, anything that is not a regular file, files of another user, files with any group or other permission bit, files over 1024 bytes and files holding a zero byte.
- The phrase file is plain text. `DESIGN.md` section 9 calls for storage encrypted at rest; that belongs to the storage port and is not done here.

## 9. What signing and coin selection will need

From this library, as it stands:

- `gzw_bip86_tweaked_keypair` gives the key pair for a key-path spend, already checked against the output key. Signing is `secp256k1_schnorrsig_sign32(ctx, sig, sighash, &keypair, aux_rand)`; the BIP 340 vectors and the BIP 341 key-path vector run against the pinned library in `test_wallet_vectors`.
- `gzw_bip86_output_from_xpub` gives scriptPubKeys to watch from the account public key alone, so the chain view never needs a private key.
- `gzw_p2tr_address_decode` and `gzw_segwit_address_decode` validate a destination address for the right network.

Not here yet, and needed:

1. **The signature hash** (BIP 341 `SigMsg`, with the annex and the amounts and scriptPubKeys of every input). The imported `tx_builder.c` and `tapscript.c` have pieces of it for the factory's transactions; whether they are usable for wallet spends has to be established the way `hd_key.c` was. The official vector file already fetched (`bip-0341/wallet-test-vectors.json`) has seven key-path cases with intermediate values; only the one without a script tree is used today.
2. **Auxiliary randomness for signing.** BIP 340 recommends fresh randomness per signature. The library has no randomness source by design, so the caller must hand in 32 bytes, as it hands in entropy for phrases.
3. **Verify after signing.** Every signature should be verified against the output key before it leaves the wallet, as BIP 340 recommends against fault attacks.
4. **Scanning by index with a gap limit**, including the rule in section 2 for an index that has no key.
5. **scriptPubKeys for destinations of any witness version** (`gzw_segwit_address_decode` returns the version and program; the script is `OP_n <program>`), and a decision on whether to pay to legacy Base58 addresses at all. The library has no Base58 address code.
6. **Amounts, fees and dust**: nothing in this library knows about amounts. The imported `fee.c` is the starting point.
7. **A script path**, if the wallet ever commits to scripts: `gzw_taproot_output_key` handles the no-script case only, and reports the output key's parity, which a control block needs.
8. **Secret lifetime across a signing session**: today each call derives from the master key and wipes. A wallet that signs many inputs will want the account key held for the session; where it is held, and for how long, is a decision for the node layer.

## 10. Tests and how they are run

| Test | What it is | Where it runs |
|---|---|---|
| `wallet_vectors` | 162 official vectors | CTest, CI, both builds |
| `wallet_keys` | unit tests | CTest, CI, both builds |
| `wallet_rare` | BIP 32 invalid cases forced through a wrapped HMAC | CTest, CI, both builds |
| `wallet_tool`, `wallet_tool_faults` | the tool, and the tool with failing system calls | CTest, CI, both builds |
| `wallet_keys_no_io` and five `wallet_no_io_rejects_*` | section 6 | CTest, CI, both builds |
| `wallet_break_checks` | every protection damaged in turn; a test must fail | CTest label `slow`, builds without sanitizers, CI. Leave out with `ctest -LE slow` or `-DGZW_BREAK_CHECKS=OFF` |
| `wallet/tests/crosscheck.py` | the same address from embit and buidl | by hand; needs third-party Python packages and a phrase file |
