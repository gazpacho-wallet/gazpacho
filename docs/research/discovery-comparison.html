Finding lobbies: six designs, one recommendation

Updated for the ideas ledger (A1, A3, A6): one factory bit (a host is whoever sends beacons), a per-connection "lobby store" flag, immediate relay, store nodes, and a pool request.

Short answer

  • Best design: D (feature bits, host queries, and a capped beacon overlay), with Nostr kept as an optional fallback.
  • Best peering technique: pick overlay peers yourself from the Lightning gossip graph, not from what other peers tell you. Lightning gossip already lists every factory node, and each one paid for a funded channel. That is the strongest Sybil filter any of the precedents had.
  • Shape: 6 links (4 to 8), at least 3 that you chose yourself, at most 2 hosts, at most 2 per address group, 2 kept across restarts, one swapped daily, plus an hourly short "scout" check against a random factory node.
  • Relay: push the whole beacon (153 bytes) to every overlay link, immediately. At these volumes, "announce the id first, send on request" saves almost nothing and adds a round trip. Bitcoin's announce-then-fetch belongs one level up: the beacon is the announcement, and the listing is fetched, from a store peer first and the host last, after a random delay.
  • Catch-up: the pool request now. Later, each host numbers its beacons, so a node can catch up by trading "highest number seen per host". No sketch maths is needed below about 10,000 hosts.
  • The spec should fix now the beacon rules, immediate relay, the store flag and store duties, the fetch order, the pool request, orphan limits and misbehaviour classes. It should only reserve have-summaries and store-to-store sync. Scoring stays local and off the wire (details).
  • Nostr: keep it, as an optional fallback. Retire it only when the measured conditions in the verdict hold for six months. Taproot channel gossip comes first.

The six designs

A. Soup's coordinator plus Nostr

A coordinator checks each host's proof and posts a "vouch" on Nostr. Wallets trust the coordinator's key. This is the owner's earlier, working system.

B. Nostr listings only

Hosts post signed lobby listings on Nostr, each backed by a coin or channel. Every wallet checks the backing itself. No coordinator.

C. Hosting bit plus queries

Gossip says who hosts. A wallet asks each host, by onion message, for its lobbies. Nothing is relayed.

D. C plus beacon overlay Recommended

As C, and hosts also send a tiny signed "new lobby" beacon. Factory nodes pass it to each other over a small overlay that follows the peering rules below.

E. Naive sub-gossip

Every factory node relays every lobby announcement to every other, with no caps or peering rules.

F. Lobbies in ordinary gossip

Lobby records ride in Lightning's own gossip, so all of the roughly 6,000 public nodes carry them.

The recommended peering rules

The rules borrow from three proven systems. Bitcoin Core supplies outbound-first slots, address-group diversity, anchors and feelers. libp2p gossipsub (used by Ethereum and Filecoin) supplies the mesh size, an outbound quota and peer scoring. Lightning gossip supplies the member list and its Sybil cost.

How a beacon travels

  1. The host signs a beacon: host key, lobby digest, open height, deadline height, sequence number. 153 bytes.
  2. It sends it to all its overlay links at once (gossipsub calls this "flood publishing").
  3. Each node checks it. It needs a valid signature and a host in gossip with the F bit. The deadline must be in the future and the host must be within its cap. The node forwards it at once to every overlay link except the sender and links that already have it.
  4. If the host is not in the node's gossip yet, the beacon waits as an "orphan" for up to 20 minutes, like Bitcoin's orphan transactions. It is re-checked when the host's announcement arrives, and the sender is not blamed.
  5. Duplicates are dropped by beacon id, and an id is marked "seen" only after its signature checks out (the lesson of Bitcoin's wtxid relay).
  6. Store nodes fetch each beacon's listing after a random 0 to 60 seconds and keep it until the deadline. Other nodes remember only the id. When a wallet wants a listing it asks a store peer first ("don't have" comes back at once), then the host after a random delay.
  7. No "announce, then send on request". At 1,000 hosts that would save about 1 MB a day and cost a round trip on every beacon. That mode suits Ethereum's busy topics, not a few beacons per host per day.

Catch-up after being offline

  • On connecting, and at most once an hour, a node sends a pool request (like Bitcoin's mempool message). The peer replies with the live beacons it holds that match the request's filter.
  • Reserved for later, above about 500 hosts: send the highest sequence number held for each host, plus 4 bytes of that beacon's id (about 16 bytes per host). The peer sends only newer or different beacons. This is exact and needs no sketches.
  • Catch up from 2 peers in different address groups, so one peer cannot hide a beacon.
  • Sketch-based reconciliation (Erlay's minisketch) or range-based reconciliation (Nostr's NIP-77) are only worth it above about 10,000 hosts.

Light clients

  1. Pick 1 or 2 store nodes (2 is safer), from the built-in list, the current host, or an invitation. At least one should not be a host.
  2. Send each a pool request by onion message, through your own channel peer, with a fresh blinded reply path. The node learns that someone asked, not who. Without an onion path, use a short-lived Tor connection (Bitcoin Core's "private broadcast" works this way).
  3. Check every beacon's signature. Merge the answers: a node can leave beacons out but cannot forge one.
  4. For each new host, ask (the same node or another) for its proof: its node_announcement with the F bit, and one of its channel_announcements. Check the signatures. Then check the channel's output through your chain server: 2 or 3 lookups, cached for 144 blocks.
  5. Pick a lobby, then ask that host for the listing and terms, as in design C.

At 100 hosts the answer fits one 32 KB onion reply. At 1,000 hosts it is about ten, so the request asks for pages by host key.

When factory nodes are few

Factory nodes in gossipWhat happens
Fewer than 8Everyone links to everyone. Wallets mostly ask each host directly (design C). The overlay costs nothing and proves the code.
8 to 50Normal rules with the relaxed age floor (144 blocks). If there are too few non-hosting nodes, fill with hosts, and scout every 20 minutes instead of hourly. A built-in seed list covers nodes whose gossip is incomplete.
More than 50Full rules. The mix and diversity limits start to bite, which is what they are for.

Partitions heal by themselves. Every node draws its scouts and rotations from the whole gossip graph, not from its overlay neighbours. Any two clusters therefore keep meeting.

Honest caveat: early on, almost every factory node will be a host. Non-hosting factory nodes appear only when members or routing nodes run factory-capable software on servers. Until then the "half non-host" rule is a target, not a guarantee.

Nostr verdict

Keep Nostr as an optional fallback now. Plan to retire it, but only when every condition below has held for six months. Do not expect that before taproot channels can be announced in gossip.

What Nostr does that the overlay cannot

  • Hosts outside gossip. A host with only taproot or private channels is invisible to the overlay. Nostr with a coin anchor lists it. Taproot gossip is still an open proposal.
  • Zero-state users. A brand-new phone with no channel can read a Nostr relay over a websocket. The overlay needs a Lightning connection first.
  • Independent failure. If onion messages are rate-limited or the overlay is attacked, Nostr still works, and the reverse.
  • Full listings for browsing. Nostr can carry the whole listing. Beacons are deliberately tiny pointers.

What the overlay does better

  • No outside operators. Measured Nostr relays: the largest held 73% of posts, about 20% were down more than 40% of the time, and most free relays cannot cover their costs.
  • The Sybil cost is a funded channel, checked by every node, not a free key.
  • No coordinator, and nothing about Gazpacho users visible to non-Lightning services.
