Gazpacho's own envelope vs bLIP-56

2026-11-12. How Gazpacho's factory messages could travel inside a Lightning connection. "Ours" is the envelope in the first version of spec/messages.md (a copy is kept at notes/specs-history/messages-own-envelope.md). "bLIP-56" is the open draft at github.com/lightning/blips pull request 56, read in full on 2026-11-11 (text saved in the session scratch folder). Short answer

  • As an envelope, ours is slightly better. It uses an odd message type, which any Lightning node safely ignores. It also has less overhead and binds every message to its lobby.
  • bLIP-56's only real advantage is compatibility: other software, possibly the SuperScalar reference, and your public comment on the pull request.
  • The two are not exclusive. Our messages can stay exactly as specified and be wrapped in bLIP-56's envelope when, and only when, the other side asks for it.

What an "envelope" is here

Every Lightning message starts with a 2-byte type. Types 32,768 to 65,535 are free for custom use. An envelope is how Gazpacho uses one custom type to carry all its own messages: lobby, terms, and the signing round. The messages inside (what a ready or a round_nonces contains, and how it is signed) are the same in both options. Only the outer wrapping differs.

One Lightning rule matters most: "it's ok to be odd". A node that receives a message type it does not know ignores it if the number is odd, but closes the connection if it is even. So an even type must be agreed first, through a feature bit.

Byte layout

Ours

type52791 protocol4 bytes "gzf"+1 kind2 lobby id32 records (TLV)up to 65,495

Header after the type: 38 bytes. The lobby id is the rules fingerprint, so every message is bound to one lobby.

bLIP-56, with our messages inside

type32800 submessage2 = 4 piggyback TLV 0: protocol id2 + 32 TLV 1024 headerabout 6 kind2 lobby id32 records (TLV)up to about 65,450

Header after the type: about 76 bytes. Our own kind and lobby id stay inside. Only the 4-byte tag is replaced by bLIP-56's 32-byte protocol id.

Beyond the envelope: what else bLIP-56 defines

bLIP-56 is mostly about channels inside a factory, not about the envelope. None of this is needed for Slice 1 (forming a factory). Whether to use it is a separate decision for the channel engine (Slice 2).

bLIP-56's weak points

  • One commit, two years old, no implementation, no detailed review.
  • Written before taproot channels: its channel change flow cannot carry the nonces they need.
  • Built for a plugin attached to existing node software. Gazpacho runs its own channel engine, so the split between "node" and "plugin" is not our architecture.
  • Uses an even message type, which is less forgiving than an odd one.
  • Says nothing about creating a factory or multi-party signing, by design. Everything Gazpacho actually needs for Slice 1 lives in the opaque payload.
  • Lets the plugin tell the node to forget a channel.

The options

1. Ours only

Keep our envelope and never wrap. Simplest, and the safest on the wire. Gazpacho cannot talk to bLIP-56 software, and it walks back your public comment.

2. bLIP-56 only

Always wrap our messages in bLIP-56. Compatible from day one, at about 40 bytes per message and an even message type that depends on feature negotiation working. Ties our wire format to an unmerged draft that may change.

3. Ours, with bLIP-56 as an adapter Recommended

Our message format stays the specification. On the wire:

  • When both sides advertise bit 271 and our protocol id, the messages travel inside bLIP-56's piggyback.
  • Otherwise they use our odd type.
  • The inner bytes, and every signature, are identical either way. So the adapter is a thin layer, about a hundred lines, that can be added, changed or dropped without touching anything else.

Slice 1 talks only Gazpacho to Gazpacho, so the adapter is not needed until we meet other software. It can be built when the SuperScalar reference or a plugin is ready to test against.

4. Propose amendments to bLIP-56

Independent of 1 to 3, and later: suggest an odd message type, taproot nonces in the change flow, and no "forget" instruction without evidence. This needs your permission, since it means posting publicly.

One thing to settle with the SuperScalar session in any case: the protocol id string (for example a hash of "SuperScalar/1"). The two programs can only talk if they use the same one.
