Is it really so simple?No. The shape is simple; eight things inside it are hard. They are listed below.
Pulling in SuperScalar, or our own thing?Both. We import its foundations (about 11,000 lines) unchanged, and write everything above them new.

Relationship to the SuperScalar repoWhat we take, and what we write

  • Fixes to the imported files go to the SuperScalar repo first, and we then update our copy.
  • If we cannot wait for a fix, it goes in a short, listed patch queue, never a silent fork.

Logical layersSix layers, four of them the core

Each layer only calls the one below it. All of L0 to L5 is C, except the web screens.

The core contractAn event goes in, a list of actions comes out

The core never waits, never opens a connection and never touches a disk. It is told what happened and answers with what to do. That is what lets the same code run on a desktop, in a browser, and inside a test.

Save before send. The program around the core carries out the actions in order, and sends nothing until the save before it is safely stored. This one rule is enforced in one place, for everything. In the old code each of about 15 paths chose its own order, which is where most of its bugs came from.

Layer 2Five engines

Signing round

One engine for every group signature

Propose, collect nonces, collect partial signatures, finish. Used for creating a factory, changing liquidity, rotating and closing.

Channel

One update routine

Save the new state, send the signature, check the other side's revocation, save, release our secret. Updates that arrive mid-update wait in a queue.

Payment

Invoices and deadlines

Incoming and outgoing payments. Deadlines are worked out from how long the factory takes to exit.

Exit

Leaving without the host

Plans which transactions to publish, in what order, when each becomes valid, and how to pay their fees.

Watch

Eyes on the chain

Knows every output that matters and what to do if each one is spent.

Why one signing engine matters

Member-side safetyOne rule before every signature

"After I sign this, can I still leave alone, with at least what I'm owed?"

The member answers from its own data only. If the answer is no, it refuses and sends nothing.

In the old code each ceremony had its own checks, and several were missing. A cooperative close that paid only the host was accepted, and so was a liquidity change that emptied a member's balance. One rule, applied by the signing engine to every request, covers both of those and whatever ceremony is added later.

The same idea runs on the host's side: its funding transaction is signed only after the whole tree and every member's exit are signed.

ProposedMessages

Compact and versioned

Binary messages with typed fields that can be extended later without breaking older software.

About 15 kinds

The old code has about 100 message types, built up over several generations.

Encrypted, host key pinned

The same messages travel over an ordinary connection or a WebSocket, so the browser version needs nothing special.

The format is written as a specification in spec/, and offered to the SuperScalar repo as the candidate for the shared format.

Layer 4Chain view that cannot be lied to, only starved

  • A server cannot invent a confirmation. Gazpacho checks the proof of work on block headers and checks each confirmation against them.
  • A server can hide a transaction. So Gazpacho asks more than one, and anyone can point it at their own node.
  • Keys never leave the app.

Proving it worksTesting, from the inside out

The simulator

A whole factory in one process

  • A host, any number of members, a pretend chain and a pretend network.
  • Driven by a seed, so every failure can be replayed exactly.
  • It drops, delays and reorders messages.
  • It crashes any party at every save point and restarts it.
  • It plays scripted cheating hosts and members.
  • After every step it checks the invariants below.
Regtest scenarios

The real programs

  • Join, receive, pay, swap in.
  • Liquidity change, rotation, cooperative close.
  • Forced exit; host disappears.
  • Host publishes an old state; member publishes an old state.
  • Restart in the middle of each ceremony.
  • Chain view through a Bitcoin node and through an Electrum server.

Invariants checked at every step

  1. Money is conserved across every state change.
  2. Every member can leave alone with at least what they are owed.
  3. No party signs two different states with the same number.
  4. Nothing is sent before it is saved.
  5. No party's software publishes a state it has revoked.
  6. Every payment deadline is later than the time needed to exit.
  7. The host's funding is never signed before every exit is signed.

For each rule there is also a run with the rule switched off, which must fail. That proves the test can catch the bug it exists for.

Honest viewWhy this is not simple

1. The channel routine

It must be exactly right through crashes and reconnects. One wrong order can lose money.

2. Backups

Channel state cannot be rebuilt from a recovery phrase. It has to be saved off the device, continuously.

3. Being reachable

Members must sign at rotation and must watch the chain. Phones and browser tabs are usually asleep.

4. Exit fees

Leaving without the host needs on-chain funds for fees at the moment it is needed.

5. Time

Payment deadlines, tree timelocks and factory lifetime must agree for every tree shape.

6. The browser

It is a fragile place to keep channel state, and whoever serves the page controls the code.

7. Public servers

They can hide a transaction. In a factory, a hidden transaction can cost money.

8. The foundations

The imported tree code still has open design issues that are being fixed in the SuperScalar repo.

GapsNot designed yet

  1. The message specification, field by field.
  2. State tables for each engine.
  3. The record types in the journal.
  4. The timelock and deadline schedule in actual numbers.
  5. Paying members, not the host, at every tree output when a factory expires. This is a change to the imported tree builder.
  6. Waking members who are offline when a factory rotates.
  7. Ordinary Lightning channels for a self-contained host.

Items 1 to 4 are written during M0 and M1. Items 5 to 7 are needed before real funds, not before signet.

Three choices I need confirmed
  1. Import the foundations as a pinned copy inside our repo (recommended), not as a live link to the SuperScalar repo.
  2. Write our own compact message format now and offer it as the shared one (recommended), not reuse today's format.
  3. For item 5 above: ask the SuperScalar repo for the change (recommended), or patch our copy.
