From docs/DESIGN.md

Logical layersSix layers, four of them the core

Each layer only calls the one below it. All of L0 to L5 is C, except the screens of the local web interface, which are HTML and JavaScript served by the C program.

The core contractAn event goes in, a list of actions comes out

The core never waits, never opens a connection and never touches a disk. It is told what happened and answers with what to do. That is what lets the same code run on any machine and inside a test.

Save before send. The program around the core carries out the actions in order, and sends nothing until the save before it is safely stored. This one rule is enforced in one place, for everything. In the old code each of about 15 paths chose its own order, which is where most of its bugs came from.

Layer 2Seven engines

Signing round

One engine for every group signature

Propose, collect nonces, collect partial signatures, finish. Used for creating a factory, changing liquidity, rotating and closing.

Channel

One update routine

Save the new state, send the signature, check the other side's revocation, save, release our secret. Updates that arrive mid-update wait in a queue.

Payment

Invoices and deadlines

Incoming and outgoing payments. Deadlines are worked out from how long the factory takes to exit.

Exit

Leaving without the host

Plans which transactions to publish, in what order, when each becomes valid, and how to pay their fees.

Watch

Eyes on the chain

Knows every output that matters and what to do if each one is spent. Built so it can also run as a separate process, at home or as a service.

Lifecycle

From lobby to wind-down

Runs a factory's life: the lobby, creation, liquidity changes, rotation into the next factory, and closing.

Schedule

Knows every date that matters

Works out when the user must act: open the app, sign a rotation, move before a factory expires. Drives reminders.

Why one signing engine matters
The six messages of a signing round

Six kinds, carried as factory messages inside the Lightning connection.

Message From → to Carries
round_propose Host → member Purpose, attempt number, the parameters from which the member rebuilds the transactions, the ordered participant list, the deadlines for each step
round_nonces Member → host The member's public nonce for each of its items, and the member's signature over the round identifier and those nonces
round_all_nonces Host → member For each of the member's items: every signer's public nonce with that signer's signature
round_partial_sigs Member → host The member's partial signature for each of its items, and the member's signature over the round identifier, a digest of the nonce set it used, and those partial signatures
round_complete Host → member The final signatures for every transaction on the member's exit path
round_abort Either way A reason, and evidence where fault can be shown

Parameters are sent, not transactions. A member builds the transactions itself.

Nonce sets for large factories are sent as a sequence of messages, one per item, ending with a marker that the set is complete.

From spec/signing-round.md

The steps, one by one
  1. Propose. The host sends round_propose to every signer.
  2. Check. Each member rebuilds the transactions, computes the round identifier, and runs the safe-to-sign checks. If they fail it sends round_abort and stops.
  3. Nonces. Each member generates a fresh secret nonce per item and sends the public parts in round_nonces.
  4. Distribute. When the host has every signer's nonces, it sends round_all_nonces.
  5. Verify and sign. Each member checks every nonce's signature, confirms its own nonces are included unchanged, runs the safe-to-sign checks again, stores its record of what it is about to sign (see safety-rule.md, check C7), then sends round_partial_sigs.
  6. Verify. The host verifies each partial signature as it arrives.
  7. Complete. When all are in and valid, the host combines them, verifies each final signature, and sends round_complete.
  8. Accept. Each member verifies the final signatures. Only then does it add the new transactions to what it holds.

From spec/signing-round.md

Rules for the one-time signing secrets

From BIP 327, which says a secret nonce must never be used to sign twice, since that can reveal the signer's key.

  • A secret nonce is generated from fresh randomness supplied to the core, together with the member's key, the aggregate key and the message when known.
  • It lives in memory only. It is never written to storage and never included in a backup.
  • It is erased as soon as it has been used to sign, or the round ends for any reason.
  • If the program restarts during a round, the round is over for that member. It will take part in the next attempt with new nonces.
  • A partial signature is produced only after the complete nonce set for that item has been received and checked.

From spec/signing-round.md

Proving who broke a round

BIP 327 lets honest parties identify a signer who sent a bad partial signature, provided contributions cannot be tampered with in transit. It warns that whoever combines the nonces could otherwise blame an honest signer, and it says nothing about convincing a third party. The scheme below is our extension to cover both.

Every contribution is signed by its author, with the same key that takes part in the group signature:

  • a member's round_nonces is signed over the round identifier and the nonces;
  • a member's round_partial_sigs is signed over the round identifier, a digest of the full nonce set the member used, and the partial signatures.

What this proves:

Fault Evidence Convinces a third party?
A member sent a bad partial signature Its signed nonces, its signed partial signature naming the nonce set, and that nonce set (each nonce signed by its owner). Anyone can run the standard verification and see it fail Yes
The host changed someone's nonce before passing it on The changed nonce does not carry its owner's signature, so members reject it in step 5 Not needed; it is caught at once
The host gave different members different nonces of its own Two nonces for the same round and item, both signed by the host Yes
The host claims a member's partial signature is bad when it is not The member's signed message names the nonce set it used; verification against that set succeeds Yes, the claim is disproved
Someone did not answer Nothing No. Silence can only be observed, not proved

After a fault: the faulty or silent signers are removed together and the host starts a new attempt, with a new round identifier, for those who remain. The host's terms say how many attempts are made and what happens if too few members remain.

From spec/signing-round.md

Never left half-finished

The danger in any round is that the host ends up holding complete signatures while a member does not.

  • A member treats a round as finished only when it holds valid final signatures for its whole exit path. Until then it behaves as if only the previous state exists: it accepts no payment and releases no secret that depends on the new one.
  • Creation: members have nothing at stake, and the host signs funding last.
  • Later rounds: the safe-to-sign checks require that the new state is at least as good for the member as the old one, and that the member's exit from any new output is signed before the transaction that creates it. So a host that withholds round_complete gains nothing: publishing the new state pays the member correctly, and the member can still use the old one.
  • A member in the Unfinished state asks again on reconnect. If the host never answers, the member exits using what it holds.

Open points on the signing round
  1. Review of section 7 by someone expert in MuSig2.
  2. Whether the host should send its own partial signatures first, and pass every member's partial signatures to the others, so that members can complete transactions themselves and the host is never the only one holding the result.
  3. Which key signs contributions. The factory key is the natural choice. Whether signing other messages with it is acceptable needs checking.
  4. Size. How nonce sets are split for the largest factories, and the largest round we support.
  5. Generating nonces early, at the ready check, to save a step. BIP 327 permits it with care; it conflicts with nothing above but removes one of the standard's safeguards.

Member-side safetyOne rule before every signature

"After I sign this, can I still leave alone, with at least what I'm owed?"

The member answers from its own data only. If the answer is no, it refuses and sends nothing.

In the old code each ceremony had its own checks, and several were missing. A cooperative close that paid only the host was accepted, and so was a liquidity change that emptied a member's balance. One rule, applied by the signing engine to every request, covers both of those and whatever ceremony is added later.

The same idea runs on the host's side: its funding transaction is signed only after the whole tree and every member's exit are signed.

From the review. "What I can leave with" has to account for timelocks, payments in flight and fees. So the rule gets a precise written definition and its own test suite before any engine relies on it.

Three more rules the review added

Signing secrets are never stored

If a signing round is interrupted, it is abandoned and restarted with fresh secrets.

A restored backup never publishes

An app restored from backup asks the host to prove the latest state and waits for the host to close. Publishing an old copy would look like cheating.

Exit fees come from the host's side

The host is the funder, so the base fee on tree and channel transactions is built in. A member's own on-chain coins are only needed to raise the fee when the chain is busy.

The nine checks a member's software runs

A request is safe to sign only if all of these hold. Each is checked against data the member's software built or stored itself.

C1. Rebuilt, not received. The member's software constructs every transaction in the request itself, from the host's signed terms, the agreed ordered list of participant keys, and the member's own stored state. It signs only digests it computed. It never signs a transaction or digest supplied by another party.

C2. Own outputs are recognised by own keys. The member's software identifies which outputs are the member's by deriving the scripts from its own keys. Labels, indexes or positions stated in the request are not trusted.

C3. Value. The exit value of the resulting set is at least the amount owed after the request (section 4).

C4. Every state the adversary could publish is covered. For every transaction in the resulting set that the adversary could publish, including ones the request is meant to replace, one of these is true: - publishing it leaves the member able to reach at least the owed amount; or - the member holds what is needed to cancel it in time and still reach the owed amount.

C5. Time. The exit time of the resulting set, plus a margin, ends before the earliest moment at which anyone else gains a competing claim on any output on the member's exit path. Today the imported tree gives the host such a claim at each node's timeout, so that timeout bounds the exit.

C6. Children before parents. The member does not help complete a signature on a transaction that creates an output unless it already holds its own fully signed exit from that output. For example, a new channel commitment on a new leaf output is fully signed and in the member's hands before the member signs the leaf transaction that creates that output.

C7. One state per number. The member never contributes to two different transactions for the same position and state number in the same factory. Before sending a partial signature it stores a record of what it signed for that position and number, and refuses anything different later.

C8. Terms. The parameters used to build the transactions match the host's signed terms, and the terms and the actual member count satisfy the member's own conditions.

C9. Nothing in flight is stranded. A request that closes or replaces a channel is refused while a payment is in flight on it, unless the resulting set still lets the member claim or reclaim that payment.

If any check fails, the member's software sends nothing for that request, tells the host it refused, and keeps its held set unchanged.

What the member is owed, operation by operation

Always from the member's own records, never from the request.

Operation Owed after the request
Creating a factory Zero. Members start with nothing
A payment in the channel The balance after the payment the member itself authorised or received, plus payments in flight the member can claim
A liquidity change on the member's leaf The same channel balance as before. Liquidity may move toward the member, never away from the member's balance
A change to a layer above the leaf Unchanged
Rotation into a new factory The same total, across the old and new factories together, at every step
A cooperative close The channel balance, paid to a script the member's software derived
Another member's leaf or branch Unchanged; and normally the member is not a signer at all

From spec/safety-rule.md

How exit value and exit time are worked out

The exit value of a set is computed by the member's software as follows.

  1. Find the member's exit path in the set: the newest fully signed transaction at each position from the funding output down, ending in outputs whose scripts the member alone can satisfy.
  2. Add up those final outputs.
  3. Subtract any fee the member must add that is not already built into the transactions.
  4. For payments in flight, count only those the member can certainly claim: it knows the secret and the deadline leaves enough time (section 6).
  5. Apply C4: if the adversary can publish a different transaction at some position, take the lowest result over every such choice, after the member's best available response.

The answer is the least the member can end up with. It must be at least the owed amount.

From spec/safety-rule.md

The host's side

The host's software runs the same module with the roles exchanged, plus three rules of its own.

H1. Funding last. The host does not sign the transaction that funds a factory until every tree transaction is fully signed and verified.

H2. Every partial signature is verified as it arrives, against its sender's key and nonce.

H3. No credit before it is covered. The host does not treat an operation as complete, and does not act on it for a member (forward a payment, release a secret), until the transactions that protect the host in the new state are fully signed.

From spec/safety-rule.md

What the rule does not protect against
  • Being ignored. A host can refuse service. The remedy is to leave.
  • A false view of the chain. The rule assumes the member's view of the chain is correct. That is the chain port's job.
  • Fees far above what was built in, if the member has no on-chain coins to add.
  • Loss of the held set. Backups are a separate mechanism.
  • Privacy. The host sees its members' payments.

From spec/safety-rule.md

Open points on the safety rule
  1. Fees. How much of the exit's fee is built in at each level, and how the member's possible top-up is counted in step 3 of section 5.
  2. Old states in the layered tree. C4 for the shrinking-timelock layers depends on the cancellation mechanism for the host's spare liquidity. That analysis has to be written out per layer.
  3. Timeouts that favour the host. C5 is stricter than it would be if every tree output paid members at expiry. If the imported tree changes, the bound changes.
  4. Rotation. "The same total across both factories at every step" needs a step-by-step statement for each rotation method.
  5. Payments in flight during a liquidity change on the same leaf.
  6. Whether C7's record can ever be safely discarded.

New in version 4The factory itself

One on-chain output, shared by the host and every member, divided by a tree of transactions that are signed in advance and normally never published.

The host funds it

Members start at zero and are paid in over Lightning. The host signs the funding last, after the whole tree is signed.

Payments stay in the channel

A payment never changes the tree. Only a change of liquidity does, and that needs just the leaf's own signers.

Layers move liquidity

Upper levels can be re-signed so the host can shift spare liquidity between members. The first release ships these layers.

It has an end date

Before it expires, members move to the host's next factory. Software that hears nothing leaves by itself in time.

How SuperScalar is meant to work

From ZmnSCPxj's posts on Delving Bitcoin (topics 1143 and 1242) as read in earlier research. Not re-read today.

  • One host and many members share one on-chain output that needs everyone's signature.
  • The host funds everything. Members start at zero and are paid in over Lightning.
  • A tree of pre-signed transactions gives each member an exit that needs nobody's help.
  • Upper layers can be re-signed to move the host's spare liquidity between members. Leaves near the bottom need only a few members online to change.
  • When a factory expires, members are meant to receive everything and the host nothing ("inversion of the timeout default"), which makes keeping the service running the host's financial duty.
  • Factories last about 30 days plus about 3 days of winding down. A new one starts daily. Members move to a new factory by paying across over Lightning.
  • A payment's final deadline must be at least the tree's total exit delay plus a margin.
  • Arity 2 is suggested near the leaves, wider higher up, and fixed (stateless) near the root.
  • Pseudo-Spilman leaves were designed for several members per leaf sharing the host's liquidity; the reference code uses one member per leaf.

From docs/KNOWLEDGE-BASE.md

Every decision about the factory
  • The full layered SuperScalar tree in the first release; the fixed tree is built first.
  • Pseudo-Spilman leaves, one member per leaf. Payments never change the tree; liquidity changes do.
  • One funder per factory: the host. Members start at zero and are paid in over Lightning.
  • The tree's shape for each size is fixed by the host's terms; members are placed in an agreed order, host first.
  • Payment deadlines are computed from the factory's exit time plus a margin; payments with less headroom are refused.
  • A member's software exits automatically before expiry if nothing else has happened.
  • At wind-down a member pays their balance into the next factory over Lightning, or co-signs a close that funds the next factory directly.
  • Target size 512 members; routine tests at smaller sizes.
  • Not in the first release: JIT channels, swap-in and swap-out, members adding their own coins, several hosts per factory.

Layer 4Chain view that cannot be lied to, only starved

  • A server cannot invent a confirmation. Gazpacho checks the proof of work on block headers and checks each confirmation against them. On signet, where blocks are signed rather than mined, it compares several servers instead.
  • A server can hide a transaction. So Gazpacho asks more than one, and anyone can point it at their own node.
  • Keys never leave the app.
Storage and backup
  • An append-only journal of typed records with periodic snapshots, encrypted at rest.
  • The encrypted journal is also the backup: one copy with the host, one the user can export.
  • A restored copy is never used to publish a channel state.

Settled in version 3The lobby: how a factory forms

Creating a factory needs everyone's software online at once. The lobby is the waiting room, and it works like a game server.

The start rule: target, minimum, deadline

Example: target 50, minimum 30, deadline in 3 hoursWhat happens
The lobby reaches 50It starts at once
Three hours pass with 30 or moreIt starts with whoever is there
Three hours pass with fewer than 30It quits, or carries the waiting members to the host's next lobby

Your conditions are locked in

A member sets conditions once. If the rules change, the app un-readies or leaves. The final guard is at signing: the app checks the real tree against those conditions.

Long gathering, short signing

Join any time and leave the program running. At the start it signs by itself within your conditions, in seconds.

Listed or unlisted, open or by invitation

Two separate settings. Invitations are QR codes. Unlisted and by invitation is private in practice.

Troublemakers

No voting. The host removes people, each member has a personal block list, and a bad signature can be proven against its sender.

Four rule profiles

Safety, Standard, Starter and Circle.

What is on Nostr

Fixed terms, ranges, size and start time. Never who joined. Live details come from the host.

Timing. A lobby has two clocks, both set by the host.

  • Gathering is long. A lobby can stay open for hours or days. Members join whenever they like, set their conditions, and can leave the app running to act for them.
  • Signing is short and happens at the scheduled start. The secrets used in a signing round are never stored, so each member's app must keep running from the first signing step to the second. If anyone drops out in between, the round restarts for everyone. A short window keeps that rare and cheap.

A host that wants a slower pace can lengthen the signing timers and accept more restarts. It is one mechanism with different timer values, not two designs.

Who can find it, and who can join. Two separate settings:

Open to anyone By invitation
Listed on Nostr A public lobby Visible, but a seat needs an invitation
Unlisted Anyone with the link can join Private in practice

Invitations are links, shown as QR codes. The host also sets what share of seats may go to members who bring nothing.

Start rule. Three numbers set by the host: a target, a minimum and a deadline.

Situation What happens
The lobby reaches the target It starts at once
The deadline arrives with at least the minimum It starts with whoever is there
The deadline arrives below the minimum It is cancelled, or the waiting members are carried over to the host's next lobby, as the host has set

Example: target 50, minimum 30, deadline in three hours. At 50 it starts immediately. At the three-hour mark it starts if there are 30 or more, and quits otherwise.

Details that make it work:

  • Only members whose software is connected and ready count. A held seat that never readies does not trigger a start.
  • Each member's own minimum is respected. A member who asked for at least 40 is not counted in a start at 35. The host's software finds the largest group whose own conditions that group satisfies.
  • Extra arrivals wait as standbys. They fill gaps left by anyone who fails to sign.
  • The count is checked again at signing. If non-signers take the group below the minimum, the factory is not created.

This is the rule Soup wallet's design had (start when full, or at a deadline if a minimum is met), and the one coinjoin coordinators use. Soup re-opened the lobby with a new deadline on a shortfall; here that is the carry-over option, and cancelling is the default.

Why it fits SuperScalar.

  • The tree is built at the moment of starting, for exactly the members present. Its shape for each size is fixed by the host's terms, so every member's software builds the same tree.
  • The host's funding scales with the number of members, and the host signs it last, after the whole tree is signed.
  • A factory's on-chain cost is shared among its members. The minimum protects the host from funding a factory too small to be worth it, and tells members they are not joining an empty one.
  • SuperScalar expects a host to start a new factory regularly. A deadline at a fixed time of day gives that rhythm; reaching the target early just starts that day's factory sooner.

All of this is separate from the signing rounds. The start rule decides when and with whom; signing then proceeds as described below.

No-shows: members who do not answer in a signing attempt are removed together and the round reruns with those who remain, plus anyone waiting on standby.

From docs/LOBBY.md

What protects a member in a lobby
  1. Member-set conditions, locked in. A member chooses conditions once: minimum number of members, minimum channel size, fee ceilings, a rule profile, and so on. The app marks the member ready only while every condition holds. If the host changes the rules so that one fails, the app un-readies or leaves.
  2. The check at signing is the real guarantee. Whatever happened in the lobby, the app checks the actual tree it is asked to sign against the member's conditions and against the safety rule, and refuses if either fails. Nothing said in a lobby can carry a member into a factory they did not agree to.
  3. Host terms are signed and versioned, so a member can show what was offered.

From docs/LOBBY.md

Dealing with troublemakers

Decided for the first version:

  • No voting and no vote-to-remove. Every member signs for themselves, the host chooses who is in the tree, and identities cost nothing, so a vote cannot bind anyone and can be bought with fake members. The owner agreed to drop it for now.
  • The host removes people. It is the host's lobby and the host's capital.
  • Each member has a personal block list. A member's app can refuse to sign a tree that contains someone on it. This is the one removal power that cannot be overridden: any single member can decline, for any reason.
  • Names, chat and rule-change requests are three settings the host can switch off. With all off, members see only a head-count, and personal block lists have nothing to act on.
  • Names are temporary and exist only for that lobby, unless a member chooses otherwise.
  • Optional self-identification. A member may attach an identity to their seat. A Nostr key or a Lightning node key is proven by signing the lobby's challenge with it. A free-text field is allowed and is always shown as unverified.
  • History is kept locally. Each app remembers who showed up and signed and who stalled, and shows it to its own user. There is no global blacklist.
  • Proof of who broke a round. Every signing message is signed by its sender. A wrong partial signature can be proven to anyone; silence cannot.

Later, as the owner expects, joining may require something scarce: control of coins, a record of signing in earlier factories, an identity the member chooses to bring. These must stay options a host can set, because a stricter host competes with someone who self-hosts with looser rules.

Adding rules later. A new joining rule usually has to look at balances, coins or other state to decide whether something is safe to sign. So adding one is normally a change to the code that decides what is safe to sign, not only to a separate rules layer (owner's correction, 2026-11-11). That code is therefore kept as one module with defined inputs and its own tests, and a new rule is a reviewed change to it. Only rules that cannot affect signing, such as how a lobby is displayed or filtered, are plain settings.

From docs/LOBBY.md

Why the factory key is never a threshold key

A threshold key (for example FROST) lets a majority sign without the minority. For the output that holds everyone's money that is the opposite of what we want: a majority, which could be fake members or the host with friends, could spend a member's money without that member. The factory key stays "everyone signs", because that is what makes it safe to share.

Threshold keys remain useful where one party splits its own key: a host run by several operators, or a member spreading their key across devices.

From docs/LOBBY.md

Removing someone from a live factory

Once a factory is live, "removing" a member can only mean one of two things, and neither takes their money:

  • they agree to leave, by co-signing a close or by paying their balance out; or
  • their branch of the tree is published, which puts their balance on chain in their own control.

Any change that needs everyone's signature, such as closing early, can be stopped by a single member. The design does not fight this with votes. It limits how often everyone is needed: day-to-day changes need only the members of one leaf or branch, and a member who will not cooperate at wind-down is left to the timeout tree while the others move on.

From docs/LOBBY.md

What is public, and host proofs

A listing on Nostr carries what rarely changes: the terms the host has fixed, the acceptable range for the others, size limits, the start time and an expiry after which the listing disappears. It never says who joined.

Anything live, such as how full the lobby is, is asked of the host directly. This keeps relays quiet and reveals less. The cost is that asking tells the host someone is interested and from which network address; connecting over Tor avoids the second.

A host may publish the factories it has funded as a track record, since the funding is on chain anyway. Whether a member can prove past participation in the same way is being looked into; it would link that member's factories together, so it could only be by choice.

The existing host proofs show control of one channel or one coin. A proof sized to the lobby a host advertises is still to be designed.

New in version 3SIPs: how the rules change

SuperScalar Improvement Proposals, modelled on the processes Bitcoin and Lightning use. A new rule usually changes the code that decides what is safe to sign, so it is requested, discussed and decided in the open.

Approval and shipping are separate decisions, so other factory software can adopt something we approve but do not ship. Four categories: Rule, Protocol, Process and Informational. There is a rule-request template with a worked example in docs/sips/.

Categories of SIP

A host connects its factory to the rest of Lightning through a regular node. Four operations are all Gazpacho needs from it.

What only the member can do

  • Signing a rotation into a new factory needs the member's key. A watcher without keys cannot do it. If the member is away, the fallback is the automatic exit before expiry, or the host publishing the member's branch.
  • Changing conditions. Anything acting for the member acts only within the conditions the member set.

  3. How the app tells the member that a watcher has fallen behind.
  4. Phone operating-system limits on background work, for the mobile app.

Proving it worksTesting, from the inside out

The simulator

A whole factory in one process

  • A host, any number of members, a pretend chain and a pretend network.
  • Driven by a seed, so every failure can be replayed exactly.
  • It drops, delays and reorders messages.
  • It crashes any party at every save point and restarts it.
  • It plays scripted cheating hosts and members.
  • After every step it checks the invariants below.
Regtest scenarios

The real programs

  • Join, receive, pay, swap in.
  • Liquidity change, rotation, cooperative close.
  • Forced exit; host disappears.
  • Host publishes an old state; member publishes an old state.
  • Restart in the middle of each ceremony.
  • Chain view through a Bitcoin node and through an Electrum server.

Invariants checked at every step

  1. Money is conserved across every state change.
  2. Every member can leave alone with at least what they are owed.
  3. No party signs two different states with the same number.
  4. Nothing is sent before it is saved.
  5. No party's software publishes a state it has revoked.
  6. Every payment deadline is later than the time needed to exit.
  7. The host's funding is never signed before every exit is signed.

For each rule there is also a run with the rule switched off, which must fail. That proves the test can catch the bug it exists for.

2. Standard vectors Official test vectors for signatures, group signing, key derivation, recovery phrases, invoices, and Lightning's own message and transaction vectors We agree with the standards byte for byte Every push
3. Engine tests One engine at a time, fed events, checked on the actions it returns Each engine's rules Every push

From docs/TESTING.md

What the simulator does

The main safety net. It is possible because the core does no input or output.

  • Schedules: a seeded generator picks operations for every party: join, pay, receive, change liquidity, update a layer, rotate, close, exit.
  • Network faults: each message may be dropped, delayed, duplicated or reordered.
  • Crashes: each party may be stopped at every point where it saves or sends, and restarted from what it saved.
  • Cheating: scripted dishonest hosts and members try each attack in the threat list: paying a close to themselves, shrinking a balance, publishing an old state, sending a bad partial signature, withholding a result, altering a nonce.
  • After every step, the invariants below are checked.
  • On failure, the seed and schedule are saved so the case becomes a permanent test.

From docs/TESTING.md

The nine invariants

Checked after every simulator step and at the end of every regtest scenario.

  1. Money is conserved across every state change.
  2. Every member can leave alone with at least what they are owed.
  3. No party signs two different states with the same number.
  4. Nothing is sent before it is saved.
  5. No secret nonce survives a restart or is used twice.
  6. No party's software publishes a state it has cancelled.
  7. Every payment deadline is later than the time needed to exit.
  8. The host's funding is never signed before every exit is signed.
  9. An honest party is never named as the cause of a failed signing round.

Honest viewWhy this is not simple

1. The channel routine

It must be exactly right through crashes and reconnects. One wrong order can lose money.

2. Backups

Channel state cannot be rebuilt from a recovery phrase. It has to be saved off the device, continuously.

3. Being reachable

Members must sign at rotation and must watch the chain. Phones and browser tabs are usually asleep.

4. Exit fees

Leaving without the host needs on-chain funds for fees at the moment it is needed.

5. Time

Payment deadlines, tree timelocks and factory lifetime must agree for every tree shape.

6. Gathering people

Everyone must be online at once to create a factory, and anyone who stalls can waste everyone's time.

7. Public servers

They can hide a transaction. In a factory, a hidden transaction can cost money.

8. The foundations

The imported tree code still has open design issues that are being fixed in the SuperScalar repo.

GapsNot designed yet

  1. The message specification, field by field.
  2. State tables for the channel, payment, exit, watch and lifecycle engines.
  3. The record types in the journal.
  4. The timelock and deadline schedule in actual numbers, for the full tree.
  5. Open points listed at the end of the two drafted specifications, including outside review of the proof-of-fault scheme.
  6. Paying members, not the host, at every tree output when a factory expires. Requested from the SuperScalar repo.
  7. Waking members who are offline when a factory rotates.
  8. Ordinary Lightning channels for a self-contained host.

  • A watching service that runs without the app. Issue 2.
  • A lobby deposit to deter people who join and never sign. Issue 3.
  • Reminders beyond the app, and acting while the member is away. Issue 4.
  • Members bringing their own coins into a factory, and several hosts sharing one factory.
