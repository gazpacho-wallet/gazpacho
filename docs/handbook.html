3. How SuperScalar is meant to work

From ZmnSCPxj's posts on Delving Bitcoin (topics 1143 and 1242) as read in earlier research. Not re-read today.

  • One host and many members share one on-chain output that needs everyone's signature.
  • The host funds everything. Members start at zero and are paid in over Lightning.
  • A tree of pre-signed transactions gives each member an exit that needs nobody's help.
  • Upper layers can be re-signed to move the host's spare liquidity between members. Leaves near the bottom need only a few members online to change.
  • When a factory expires, members are meant to receive everything and the host nothing ("inversion of the timeout default"), which makes keeping the service running the host's financial duty.
  • Factories last about 30 days plus about 3 days of winding down. A new one starts daily. Members move to a new factory by paying across over Lightning.
  • A payment's final deadline must be at least the tree's total exit delay plus a margin.
  • Arity 2 is suggested near the leaves, wider higher up, and fixed (stateless) near the root.
  • Pseudo-Spilman leaves were designed for several members per leaf sharing the host's liquidity; the reference code uses one member per leaf.

5. Decisions in force

Newest first within each area. The date is when the owner decided.

Product

  • Gazpacho is both host and member software, self-contained, C, signet first, quality before dates. (11 Nov)
  • Soup wallet is mothballed, kept for reference. The SuperScalar repo is maintained by another session. (11 Nov)
  • Home is github.com/gazpacho-wallet/gazpacho, MIT, public since 11 Nov 2026.
  • The screens are a local web interface served by the C program. No wallet-in-a-web-page. (11 Nov)

Construction

  • Full layered tree in the first release; build the fixed tree first. Pseudo-Spilman leaves, one member per leaf. JIT channels off. Target 512 members, tested at 128 or 256.
  • One funder per factory: the host, who signs funding only after the whole tree is signed. Members start at zero.
  • The factory key always needs everyone's signature. No threshold key.
  • Lightning's standard taproot channel format for the channel; the old format archived and recoverable.
  • Lightning's own wire language; factory messages inside one custom message type.
  • Members adding their own coins, several hosts per factory, swap-in and swap-out: after the first release.

Safety

  • One member-side rule before every signature. Save before send. Signing secrets never stored. A restored backup never publishes its own state.
  • Exit fees are built in from the host's side; a small on-chain reserve is recommended, not required.
  • About two weeks to respond to an old state; the watch engine can also run as a separate process.
  • New joining or safety rules are normally changes to the safe-to-sign code itself, which is kept as one small, tested module.

Forming a factory

  • A lobby like a game server, with member conditions that are locked in. Gathering is long; signing is short at a scheduled start; the host sets both timers.
  • Newcomers with no funds are the main audience; each host sets their share of seats.
  • A lobby is listed or unlisted, and open or by invitation (QR invitations).
  • Names, chat and rule-change requests can each be switched off by the host. A member may attach a proven or free-text identity; identity is new per lobby by default.
  • Listings carry fixed terms, ranges, size and start time; live details come from the host. Hosts may publish a track record.
  • All four rule profiles ship: Safety, Standard, Starter, Circle. Deposits come in the release after the first.
  • No voting and no vote-to-remove. The host removes people; each member has a personal block list; history is kept locally.
  • Listings and host proofs on Nostr; everything else direct.
  • The lobby and signing coordination are written so they can become their own library.

Hosts

  • A host links to a regular Lightning node through an adapter: LND first, then Core Lightning, then others. Later the built-in node holds ordinary channels itself.

  • Work proceeds in vertical slices on signet as soon as the engines they need are tested: form a factory, then a payment, then leaving alone. (11 Nov)

Working method

  • The owner handles outside review. This session's job is to bring the software to release candidates fit for review.
  • New rules and features go through SIPs (SuperScalar Improvement Proposals), modelled on BIPs and bLIPs. Approval and shipping are separate; the record of ACKs and NACKs is kept.
  • Review: several different AI models on every engine as it is built; outside human reviewers and red-teamers before real funds.
  • Hand-off notes are local documents the owner points the other session to.
  • Chain servers: well-known public ones first (checked list in CHAIN-SERVERS.md); our own around launch. No Bitcoin node of our own for now.
  • Reminders: in-app countdowns first; Nostr, email and phone notifications later.
  • Imported SuperScalar files are never edited here. Changes are requested from the SuperScalar repo.
  • Every safety rule has a test and a run with the rule removed that must fail.
  • Illustrated pages keep earlier versions behind a version switch.
  • Claims are checked against primary sources where money depends on them, and marked when they are not.
6. How sure we are

Checked today against a primary source or by running it

  • Lightning's message format, type ranges, typed fields and the odd/even rule (the messaging specification).
  • Peer-storage messages exist in the specification.
  • Core Lightning's dual-funding code received security fixes in four releases from August to November 2026 (its release notes).
  • LND has hold, settle and cancel for invoices built in (its interface definition).
  • Everything in section 4 marked as run, built or read on 2026-11-11.

From secondary sources only

  • Lightning's taproot channel format was merged into the specification in 2026 and ships in LND and Eclair.
  • LND is about 90% of public nodes; Core Lightning about 5%.
  • Core Lightning holds payments through a community plugin.
  • A WebSocket carrier for Lightning connections is not standardised.

Our own reasoning, not yet reviewed

  • The scheme for proving who broke a signing round.
  • That a member adding coins to their own leaf leaves other members unaffected.
  • That swap-in is safe under three conditions (confirmations first, on-chain timeout after the channel deadline, refund after timeout). The technique is long established; our statement of it was not re-checked against sources.
  • Estimates of size and effort.

Not yet known

  • Whether Eclair, LDK-based nodes and Nostr Wallet Connect can hold payments open in a way we can use.
  • The timelock and deadline numbers for the full layered tree.
  • How members who are offline at rotation are reached.
7. Risks we are carrying
  1. The chosen leaf design is unproven at size. Gazpacho's plan is one member per pseudo-Spilman leaf at up to 512 members. Nobody has run that shape above 16. It must be tested before anything is built on it; if it fails or its exits are too slow, several members per leaf is the fallback.
  2. The channel update routine must be exactly right through crashes and reconnects.
  3. Channel state cannot be rebuilt from a recovery phrase.
  4. Members must be reachable at rotation and must watch the chain.
  5. Deadlines, timelocks and factory lifetime must agree for every tree shape.
  6. Public chain servers can hide a transaction.
  7. The imported tree code still has open design issues upstream.
  8. Gathering many people to sign at once, with people who join and never sign.
  9. Privacy: a host sees all of its members' payments.

  • Builds and tests run on Gazpacho's own build server, in one folder. The server used earlier is left to the SuperScalar session.
  • The project runs no Bitcoin node of its own for now. It uses public chain servers, on signet (CHAIN-SERVERS.md).
  • Commits are authored as 8144225309 <8144225309@users.noreply.github.com>.

Gazpacho design · docs/DESIGN.md

The current design, consolidated. 2026-11-11.

How it got here, with dates, findings and superseded ideas, is in RECORD.md. Where the two differ, this file is the one in force. The illustrated version is design.html.

1. What Gazpacho is

One program that lets a person join a SuperScalar channel factory as a member or run one as a host. It carries its own small Lightning node for factory channels and an ordinary on-chain wallet, and reads the chain through Electrum-style servers or the user's own node. It needs no modified node software. First releases are signet-only; the code for mainnet exists and is switched off.

2. Where the code comes from
  • Imported unchanged from SuperScalar, pinned to a known version under core/superscalar/: tree building, group signing, timelock counter, ladder, transaction and script building, adaptor signatures, key derivation, recovery phrases, address and invoice encoding, fee helpers. 38 files. A manifest records each file's checksum, and a script refreshes the copy.
  • Written new: everything above that. SuperScalar's host and member code is the reference for behaviour, not a source of code.
  • Not edited here: a change to an imported file is requested from the SuperScalar repo. If it cannot wait it goes in a short, listed patch queue.
  • Reference results recorded from real SuperScalar runs catch any drift when the import is updated.
3. Layers
Layer Contents Source
L5 Programs gazpacho command line, host service, local web interface new
L4 Ports storage, chain view, network, clock, randomness, host's Lightning node new
L3 Node sessions, journal, timers, on-chain wallet, host terms, member and host roles new

L0 to L3 are the core: portable C with no system calls. Everything is C except the screens of the local web interface.

The lobby, the signing round engine and the proof-of-fault scheme are written without dependence on the factory code so they can be split out as a coordination library.

4. The core contract

An event goes in and a list of actions comes out. The core never waits and never touches the outside world.

  • Events: a message arrived, a timer fired, something happened on chain, the user asked for something, storage confirmed a save.
  • Actions: save records as one atomic batch, send a message, broadcast a transaction, watch a script, set a timer, tell the user.
  • Save before send. The program around the core carries out actions in order and sends nothing until the save before it is safely stored. Enforced in one place for every engine.
  • Randomness and time are handed to the core, so a whole factory can be simulated repeatably.

6. Safety

The full definition is spec/safety-rule.md. In brief:

  • One rule before every signature: sign only if, afterwards, the member can still leave alone, in time, with at least what they are owed, whatever everyone else does.
  • A member's software signs only transactions it rebuilt itself, recognises its outputs by its own keys, and never helps create an output without already holding its signed exit from it.
  • The factory key always needs everyone's signature. No threshold key.
  • Sign before fund: the host signs funding only after the whole tree is signed and verified.
  • Every partial signature is verified as it arrives.
  • Signing secrets are never stored. An interrupted round is abandoned.
  • A restored backup never publishes its own channel state. It asks the host to prove the latest and waits for the host to close.
  • Exit fees are built in from the host's side. A small on-chain reserve is recommended to members, not required.
  • Away protection: about two weeks to respond to an old state.
  • A new safety or joining rule is normally a reviewed change to the safe-to-sign module, proposed through a SIP.
7. The factory
  • The full layered SuperScalar tree in the first release; the fixed tree is built first.
  • Pseudo-Spilman leaves, one member per leaf. Payments never change the tree; liquidity changes do.
  • One funder per factory: the host. Members start at zero and are paid in over Lightning.
  • The tree's shape for each size is fixed by the host's terms; members are placed in an agreed order, host first.
  • Payment deadlines are computed from the factory's exit time plus a margin; payments with less headroom are refused.
  • A member's software exits automatically before expiry if nothing else has happened.
  • At wind-down a member pays their balance into the next factory over Lightning, or co-signs a close that funds the next factory directly.
  • Target size 512 members; routine tests at smaller sizes.
  • Not in the first release: JIT channels, swap-in and swap-out, members adding their own coins, several hosts per factory.
8. Messages and channel format
  • A Gazpacho connection is an ordinary Lightning peer connection that also carries factory messages.
  • Lightning's encrypted transport with the host's key pinned; over TCP, and over WebSocket where needed.
  • Lightning's message shape, session start and feature flags. No version numbers: unknown odd fields are skipped, unknown even ones refused.
  • Lightning's standard channel messages and its standard taproot channel format for the channel inside a leaf. The old SuperScalar channel format is archived and can be reinstated behind the channel engine's format interface.
  • Factory messages travel inside one custom message type, with an envelope naming the protocol, the factory and the message kind.
  • Large signing data is split across messages with a completion marker.
  • A member's backup is held by the host using Lightning's peer-storage messages.
  • Encoders and decoders are generated from tables in spec/, with test vectors and fuzzing.
  • The message specification itself is still to be written, and will be offered to the SuperScalar repo as the shared format.
9. Storage and backup
  • An append-only journal of typed records with periodic snapshots, encrypted at rest.
  • The encrypted journal is also the backup: one copy with the host, one the user can export.
  • A restored copy is never used to publish a channel state.
10. Chain view

Safe-to-sign rule

Specification: the checks run before every signature.

The safe-to-sign rule · spec/safety-rule.md

Specification draft 1, 2026-11-11. Status: for review. Nothing here has been reviewed by anyone outside this project.

This document defines the check a member's software runs before it contributes to any signature, and the matching check on the host's side. The code that implements it is one module, the only place where "is this safe to sign?" is decided.

1. The rule in one sentence

A member's software signs only if, once the signature exists, the member can still leave alone, in time, with at least what they are owed, whatever the host and every other member do.

2. Terms
Term Meaning
Held set Every fully signed transaction the member holds, plus the secrets it has been given for cancelling old states
Request A proposal to create new signatures: for new transactions, or for transactions that replace existing ones
Resulting set The held set as it would be if the request completed
Exit path The chain of transactions from the factory's funding output down to outputs only the member controls
Owed The amount the member is entitled to, taken from the member's own records. Defined in section 4
Exit value What the member can bring under their sole control by publishing transactions from a set, defined in section 5
Exit time The number of blocks needed to complete an exit from a set, defined in section 6
Adversary The host together with all other members. They may publish any transaction they hold a valid signature for, including old ones, at any time
3. The checks

A request is safe to sign only if all of these hold. Each is checked against data the member's software built or stored itself.

C1. Rebuilt, not received. The member's software constructs every transaction in the request itself, from the host's signed terms, the agreed ordered list of participant keys, and the member's own stored state. It signs only digests it computed. It never signs a transaction or digest supplied by another party.

C2. Own outputs are recognised by own keys. The member's software identifies which outputs are the member's by deriving the scripts from its own keys. Labels, indexes or positions stated in the request are not trusted.

C3. Value. The exit value of the resulting set is at least the amount owed after the request (section 4).

C4. Every state the adversary could publish is covered. For every transaction in the resulting set that the adversary could publish, including ones the request is meant to replace, one of these is true: - publishing it leaves the member able to reach at least the owed amount; or - the member holds what is needed to cancel it in time and still reach the owed amount.

C5. Time. The exit time of the resulting set, plus a margin, ends before the earliest moment at which anyone else gains a competing claim on any output on the member's exit path. Today the imported tree gives the host such a claim at each node's timeout, so that timeout bounds the exit.

C6. Children before parents. The member does not help complete a signature on a transaction that creates an output unless it already holds its own fully signed exit from that output. For example, a new channel commitment on a new leaf output is fully signed and in the member's hands before the member signs the leaf transaction that creates that output.

C7. One state per number. The member never contributes to two different transactions for the same position and state number in the same factory. Before sending a partial signature it stores a record of what it signed for that position and number, and refuses anything different later.

C8. Terms. The parameters used to build the transactions match the host's signed terms, and the terms and the actual member count satisfy the member's own conditions.

C9. Nothing in flight is stranded. A request that closes or replaces a channel is refused while a payment is in flight on it, unless the resulting set still lets the member claim or reclaim that payment.

If any check fails, the member's software sends nothing for that request, tells the host it refused, and keeps its held set unchanged.

4. What the member is owed

Always from the member's own records, never from the request.

Operation Owed after the request
Creating a factory Zero. Members start with nothing
A payment in the channel The balance after the payment the member itself authorised or received, plus payments in flight the member can claim
A liquidity change on the member's leaf The same channel balance as before. Liquidity may move toward the member, never away from the member's balance
A change to a layer above the leaf Unchanged
Rotation into a new factory The same total, across the old and new factories together, at every step
A cooperative close The channel balance, paid to a script the member's software derived
Another member's leaf or branch Unchanged; and normally the member is not a signer at all
5. Exit value

The exit value of a set is computed by the member's software as follows.

  1. Find the member's exit path in the set: the newest fully signed transaction at each position from the funding output down, ending in outputs whose scripts the member alone can satisfy.
  2. Add up those final outputs.
  3. Subtract any fee the member must add that is not already built into the transactions.
  4. For payments in flight, count only those the member can certainly claim: it knows the secret and the deadline leaves enough time (section 6).
  5. Apply C4: if the adversary can publish a different transaction at some position, take the lowest result over every such choice, after the member's best available response.

The answer is the least the member can end up with. It must be at least the owed amount.

6. Exit time
  1. Sum the waiting periods on the exit path: each relative timelock, plus a confirmation allowance for each transaction.
  2. Add the response window for a cancelled channel state, if the member's own channel transaction is delayed by one.
  3. The result, counted from now, must end before the bound in C5, with a margin set by the terms.

A payment may be accepted only if its deadline is later than the exit time plus a margin, so that the member could still claim it on chain.

7. The host's side

The host's software runs the same module with the roles exchanged, plus three rules of its own.

H1. Funding last. The host does not sign the transaction that funds a factory until every tree transaction is fully signed and verified.

H2. Every partial signature is verified as it arrives, against its sender's key and nonce.

H3. No credit before it is covered. The host does not treat an operation as complete, and does not act on it for a member (forward a payment, release a secret), until the transactions that protect the host in the new state are fully signed.

8. What this rule does not protect against
  • Being ignored. A host can refuse service. The remedy is to leave.
  • A false view of the chain. The rule assumes the member's view of the chain is correct. That is the chain port's job.
  • Fees far above what was built in, if the member has no on-chain coins to add.
  • Loss of the held set. Backups are a separate mechanism.
  • Privacy. The host sees its members' payments.
9. How it is tested

For every check C1 to C9 and H1 to H3:

  1. A scenario in the simulator where the other side sends a request that violates the check. The software must refuse and its held set must be unchanged.
  2. The same scenario with the check switched off. The simulator's independent accounting, which replays what each party could actually publish on its pretend chain, must then show a loss. If it does not, either the check is unnecessary or the test is too weak.
  3. Honest scenarios for each operation, which must still succeed.

The simulator's accounting computes exit value independently of this module, from the transactions alone, so a mistake in the module is not hidden by the same mistake in the test.

10. Open points
  1. Fees. How much of the exit's fee is built in at each level, and how the member's possible top-up is counted in step 3 of section 5.
  2. Old states in the layered tree. C4 for the shrinking-timelock layers depends on the cancellation mechanism for the host's spare liquidity. That analysis has to be written out per layer.
  3. Timeouts that favour the host. C5 is stricter than it would be if every tree output paid members at expiry. If the imported tree changes, the bound changes.
  4. Rotation. "The same total across both factories at every step" needs a step-by-step statement for each rotation method.
  5. Payments in flight during a liquidity change on the same leaf.
  6. Whether C7's record can ever be safely discarded.

Signing round

Specification: messages, steps, one-time secrets, proving who broke a round.

The signing round · spec/signing-round.md

Specification draft 1, 2026-11-11. Status: for review. The part on proving fault (section 7) is this project's own design and has had no outside review.

A signing round produces group signatures for a set of transactions. One engine runs every round in Gazpacho: creating a factory, changing a leaf, updating a layer, rotating, closing. It follows the MuSig2 standard (BIP 327) and uses the imported signing code.

1. Parties and scope
  • The coordinator is the host. It is also a signer in every transaction.
  • Members are the other signers. Each talks only to the host.
  • A round covers one or more items. Each item is one transaction input to be signed, with its own set of signers. A member signs only the items on its own path.
  • The round engine does not decide whether signing is safe. It asks the safe-to-sign module (safety-rule.md) and obeys it.
2. What identifies a round
round_id = hash( protocol name, factory identifier, purpose, attempt number,
                 ordered list of participant keys, digest of every item )

Anything that changes any of these is a different round, with fresh nonces. Participants are ordered by an agreed rule, host first, so every party computes the same identifier and builds the same transactions.

3. Messages

Six kinds, carried as factory messages inside the Lightning connection.

Message From → to Carries
round_propose Host → member Purpose, attempt number, the parameters from which the member rebuilds the transactions, the ordered participant list, the deadlines for each step
round_nonces Member → host The member's public nonce for each of its items, and the member's signature over the round identifier and those nonces
round_all_nonces Host → member For each of the member's items: every signer's public nonce with that signer's signature
round_partial_sigs Member → host The member's partial signature for each of its items, and the member's signature over the round identifier, a digest of the nonce set it used, and those partial signatures
round_complete Host → member The final signatures for every transaction on the member's exit path
round_abort Either way A reason, and evidence where fault can be shown

Parameters are sent, not transactions. A member builds the transactions itself.

Nonce sets for large factories are sent as a sequence of messages, one per item, ending with a marker that the set is complete.

4. Steps
  1. Propose. The host sends round_propose to every signer.
  2. Check. Each member rebuilds the transactions, computes the round identifier, and runs the safe-to-sign checks. If they fail it sends round_abort and stops.
  3. Nonces. Each member generates a fresh secret nonce per item and sends the public parts in round_nonces.
  4. Distribute. When the host has every signer's nonces, it sends round_all_nonces.
  5. Verify and sign. Each member checks every nonce's signature, confirms its own nonces are included unchanged, runs the safe-to-sign checks again, stores its record of what it is about to sign (see safety-rule.md, check C7), then sends round_partial_sigs.
  6. Verify. The host verifies each partial signature as it arrives.
  7. Complete. When all are in and valid, the host combines them, verifies each final signature, and sends round_complete.
  8. Accept. Each member verifies the final signatures. Only then does it add the new transactions to what it holds.
5. States

Member

State Leaves on
Idle round_propose → Checking
Checking Checks pass → Nonces sent. Checks fail → Aborted
Nonces sent round_all_nonces valid → Signed. Deadline or invalid → Aborted
Signed round_complete valid → Complete. Deadline → Unfinished
Complete
Aborted Secret nonces erased
Unfinished The member has signed but does not hold the result. See section 8

Host: Collecting nonces → Collecting partial signatures → Complete, or Failed with a list of who did not answer or sent something invalid.

6. Rules for secret nonces

From BIP 327, which says a secret nonce must never be used to sign twice, since that can reveal the signer's key.

  • A secret nonce is generated from fresh randomness supplied to the core, together with the member's key, the aggregate key and the message when known.
  • It lives in memory only. It is never written to storage and never included in a backup.
  • It is erased as soon as it has been used to sign, or the round ends for any reason.
  • If the program restarts during a round, the round is over for that member. It will take part in the next attempt with new nonces.
  • A partial signature is produced only after the complete nonce set for that item has been received and checked.
7. Who broke the round

BIP 327 lets honest parties identify a signer who sent a bad partial signature, provided contributions cannot be tampered with in transit. It warns that whoever combines the nonces could otherwise blame an honest signer, and it says nothing about convincing a third party. The scheme below is our extension to cover both.

Every contribution is signed by its author, with the same key that takes part in the group signature:

  • a member's round_nonces is signed over the round identifier and the nonces;
  • a member's round_partial_sigs is signed over the round identifier, a digest of the full nonce set the member used, and the partial signatures.

What this proves:

Fault Evidence Convinces a third party?
A member sent a bad partial signature Its signed nonces, its signed partial signature naming the nonce set, and that nonce set (each nonce signed by its owner). Anyone can run the standard verification and see it fail Yes
The host changed someone's nonce before passing it on The changed nonce does not carry its owner's signature, so members reject it in step 5 Not needed; it is caught at once
The host gave different members different nonces of its own Two nonces for the same round and item, both signed by the host Yes
The host claims a member's partial signature is bad when it is not The member's signed message names the nonce set it used; verification against that set succeeds Yes, the claim is disproved
Someone did not answer Nothing No. Silence can only be observed, not proved

After a fault: the faulty or silent signers are removed together and the host starts a new attempt, with a new round identifier, for those who remain. The host's terms say how many attempts are made and what happens if too few members remain.

8. Never left half-finished

The danger in any round is that the host ends up holding complete signatures while a member does not.

  • A member treats a round as finished only when it holds valid final signatures for its whole exit path. Until then it behaves as if only the previous state exists: it accepts no payment and releases no secret that depends on the new one.
  • Creation: members have nothing at stake, and the host signs funding last.
  • Later rounds: the safe-to-sign checks require that the new state is at least as good for the member as the old one, and that the member's exit from any new output is signed before the transaction that creates it. So a host that withholds round_complete gains nothing: publishing the new state pays the member correctly, and the member can still use the old one.
  • A member in the Unfinished state asks again on reconnect. If the host never answers, the member exits using what it holds.
9. Timers

Set by the host's terms and visible to members before they join. Starting values, to be tuned on signet:

Step Default
Ready check before the first attempt 60 seconds
Nonces, per attempt 30 seconds
Partial signatures, per attempt 30 seconds
Attempts 3

A host may set longer signing timers. Members' software must then stay running throughout, because of section 6.

10. Use of the imported code
Step Function in core/superscalar
Build the tree factory_init_from_pubkeys, factory_set_arity, factory_set_funding, factory_build_tree, with sequential placement selected so member order never depends on a sort
Start signing for an item factory_session_init_node
Generate a nonce musig_generate_nonce
Record a signer's nonce factory_session_set_nonce, then factory_session_finalize_node
Produce a partial signature musig_create_partial_sig
Verify a partial signature musig_verify_partial_sig. The imported code never calls this itself; the round engine must

The imported nonce generator reads randomness from the operating system directly. Until that is changed upstream, the engine cannot be simulated repeatably through that function; the hand-off note asks for a way to supply randomness.

11. How it is tested
  1. Honest rounds of every purpose, at several sizes.
  2. Each message dropped, delayed, duplicated and reordered, at each step.
  3. A crash and restart of each party at each step. No secret nonce may survive a restart, and no party may sign twice.
  4. Each fault in section 7, checking that the right party is named and the evidence verifies, and that an honest party cannot be framed.
  5. A host that withholds round_complete: the member must lose nothing.
  6. Removal of each rule in turn (nonce signature check, partial signature verification, the C7 record), each of which must make a specific test fail.
  7. Fuzzing of every message decoder.
12. Open points
  1. Review of section 7 by someone expert in MuSig2.
  2. Whether the host should send its own partial signatures first, and pass every member's partial signatures to the others, so that members can complete transactions themselves and the host is never the only one holding the result.
  3. Which key signs contributions. The factory key is the natural choice. Whether signing other messages with it is acceptable needs checking.
  4. Size. How nonce sets are split for the largest factories, and the largest round we support.
  5. Generating nonces early, at the ready check, to save a step. BIP 327 permits it with care; it conflicts with nothing above but removes one of the standard's safeguards.

The lobby

How a factory forms: start rule, member conditions, troublemakers, what is public.

The lobby: how a factory forms · docs/LOBBY.md

Design note 2, 2026-11-11. Based on LOBBY-research.md and the owner's decisions. Items marked (open) are in OPEN-QUESTIONS.md.

The idea

Creating a factory needs the host and every member online at the same moment to sign. The lobby is the waiting room. It works like a game server: a host opens a lobby with rules, people join, and it starts when its conditions are met.

Nobody has money at risk in a lobby. Members put in nothing at creation, and the host signs its funding only after the whole tree is signed. The cost of bad behaviour is wasted time and, for the host, idle capital.

Stages
Stage What happens Who moves it on
Draft The host sets the rules Host
Open Listed; members join by connecting directly to the host Members joining; the start rule
Ready check Each member's app confirms it is present and its conditions hold Timer
Signing The group signing rounds; up to three attempts The signing engine
Funding The host funds the factory Host; the chain
Active The factory is live
Cancelled / Failed Too few members, or signing could not complete

Timing. A lobby has two clocks, both set by the host.

  • Gathering is long. A lobby can stay open for hours or days. Members join whenever they like, set their conditions, and can leave the app running to act for them.
  • Signing is short and happens at the scheduled start. The secrets used in a signing round are never stored, so each member's app must keep running from the first signing step to the second. If anyone drops out in between, the round restarts for everyone. A short window keeps that rare and cheap.

A host that wants a slower pace can lengthen the signing timers and accept more restarts. It is one mechanism with different timer values, not two designs.

Who can find it, and who can join. Two separate settings:

Open to anyone By invitation
Listed on Nostr A public lobby Visible, but a seat needs an invitation
Unlisted Anyone with the link can join Private in practice

Invitations are links, shown as QR codes. The host also sets what share of seats may go to members who bring nothing.

Start rule. Three numbers set by the host: a target, a minimum and a deadline.

Situation What happens
The lobby reaches the target It starts at once
The deadline arrives with at least the minimum It starts with whoever is there
The deadline arrives below the minimum It is cancelled, or the waiting members are carried over to the host's next lobby, as the host has set

Example: target 50, minimum 30, deadline in three hours. At 50 it starts immediately. At the three-hour mark it starts if there are 30 or more, and quits otherwise.

Details that make it work:

  • Only members whose software is connected and ready count. A held seat that never readies does not trigger a start.
  • Each member's own minimum is respected. A member who asked for at least 40 is not counted in a start at 35. The host's software finds the largest group whose own conditions that group satisfies.
  • Extra arrivals wait as standbys. They fill gaps left by anyone who fails to sign.
  • The count is checked again at signing. If non-signers take the group below the minimum, the factory is not created.

This is the rule Soup wallet's design had (start when full, or at a deadline if a minimum is met), and the one coinjoin coordinators use. Soup re-opened the lobby with a new deadline on a shortfall; here that is the carry-over option, and cancelling is the default.

Why it fits SuperScalar.

  • The tree is built at the moment of starting, for exactly the members present. Its shape for each size is fixed by the host's terms, so every member's software builds the same tree.
  • The host's funding scales with the number of members, and the host signs it last, after the whole tree is signed.
  • A factory's on-chain cost is shared among its members. The minimum protects the host from funding a factory too small to be worth it, and tells members they are not joining an empty one.
  • SuperScalar expects a host to start a new factory regularly. A deadline at a fixed time of day gives that rhythm; reaching the target early just starts that day's factory sooner.

All of this is separate from the signing rounds. The start rule decides when and with whom; signing then proceeds as described below.

No-shows: members who do not answer in a signing attempt are removed together and the round reruns with those who remain, plus anyone waiting on standby.

What protects a member
  1. Member-set conditions, locked in. A member chooses conditions once: minimum number of members, minimum channel size, fee ceilings, a rule profile, and so on. The app marks the member ready only while every condition holds. If the host changes the rules so that one fails, the app un-readies or leaves.
  2. The check at signing is the real guarantee. Whatever happened in the lobby, the app checks the actual tree it is asked to sign against the member's conditions and against the safety rule, and refuses if either fails. Nothing said in a lobby can carry a member into a factory they did not agree to.
  3. Host terms are signed and versioned, so a member can show what was offered.
Dealing with troublemakers

Decided for the first version:

  • No voting and no vote-to-remove. Every member signs for themselves, the host chooses who is in the tree, and identities cost nothing, so a vote cannot bind anyone and can be bought with fake members. The owner agreed to drop it for now.
  • The host removes people. It is the host's lobby and the host's capital.
  • Each member has a personal block list. A member's app can refuse to sign a tree that contains someone on it. This is the one removal power that cannot be overridden: any single member can decline, for any reason.
  • Names, chat and rule-change requests are three settings the host can switch off. With all off, members see only a head-count, and personal block lists have nothing to act on.
  • Names are temporary and exist only for that lobby, unless a member chooses otherwise.
  • Optional self-identification. A member may attach an identity to their seat. A Nostr key or a Lightning node key is proven by signing the lobby's challenge with it. A free-text field is allowed and is always shown as unverified.
  • History is kept locally. Each app remembers who showed up and signed and who stalled, and shows it to its own user. There is no global blacklist.
  • Proof of who broke a round. Every signing message is signed by its sender. A wrong partial signature can be proven to anyone; silence cannot.

Later, as the owner expects, joining may require something scarce: control of coins, a record of signing in earlier factories, an identity the member chooses to bring. These must stay options a host can set, because a stricter host competes with someone who self-hosts with looser rules.

Adding rules later. A new joining rule usually has to look at balances, coins or other state to decide whether something is safe to sign. So adding one is normally a change to the code that decides what is safe to sign, not only to a separate rules layer (owner's correction, 2026-11-11). That code is therefore kept as one module with defined inputs and its own tests, and a new rule is a reviewed change to it. Only rules that cannot affect signing, such as how a lobby is displayed or filtered, are plain settings.

Why not threshold signatures

A threshold key (for example FROST) lets a majority sign without the minority. For the output that holds everyone's money that is the opposite of what we want: a majority, which could be fake members or the host with friends, could spend a member's money without that member. The factory key stays "everyone signs", because that is what makes it safe to share.

Threshold keys remain useful where one party splits its own key: a host run by several operators, or a member spreading their key across devices.

Removing someone from a live factory

Once a factory is live, "removing" a member can only mean one of two things, and neither takes their money:

  • they agree to leave, by co-signing a close or by paying their balance out; or
  • their branch of the tree is published, which puts their balance on chain in their own control.

Any change that needs everyone's signature, such as closing early, can be stopped by a single member. The design does not fight this with votes. It limits how often everyone is needed: day-to-day changes need only the members of one leaf or branch, and a member who will not cooperate at wind-down is left to the timeout tree while the others move on.

Profiles

Named presets of rules. All four ship in the first release.

Profile For In short
Safety Cautious users Simple operation only; optional features off
Standard Most public lobbies The defaults
Starter People arriving with no funds Small channels, low requirements, limited seats
Circle People who know each other Unlisted and by invitation
What is public

A listing on Nostr carries what rarely changes: the terms the host has fixed, the acceptable range for the others, size limits, the start time and an expiry after which the listing disappears. It never says who joined.

Anything live, such as how full the lobby is, is asked of the host directly. This keeps relays quiet and reveals less. The cost is that asking tells the host someone is interested and from which network address; connecting over Tor avoids the second.

A host may publish the factories it has funded as a track record, since the funding is on chain anyway. Whether a member can prove past participation in the same way is being looked into; it would link that member's factories together, so it could only be by choice.

The existing host proofs show control of one channel or one coin. A proof sized to the lobby a host advertises is still to be designed.

A separate library

The lobby, the signing round engine and the proof-of-fault scheme together are a general tool for coordinating large group signatures. They are written with no dependence on the factory code, so they can be split out as their own library.

Host's Lightning node

Lightning nodes a host can link to · docs/HOST-NODES.md

Working list, 2026-11-11. A host connects its factory to the rest of Lightning through a regular node. Gazpacho needs four operations from it:

  1. Pay an invoice with a spending limit and a deadline, and return the payment secret.
  2. Create an invoice for a payment hash whose secret the node does not know, and hold the incoming payment open.
  3. Settle a held payment.
  4. Cancel a held payment.

Every node can do the first. The other three are the deciding factor.

Testing

Levels, the simulator, invariants, scenarios, the bar for a release candidate.

Testing plan · docs/TESTING.md

How Gazpacho is shown to work, from single functions up to public test networks. Updated 2026-11-11.

Principles
  1. Every safety rule has two tests: one showing the rule stops the attack, and one with the rule removed that must show a loss. The second proves the first can catch the bug it exists for.
  2. The checker is independent of the code it checks. Money is counted from the transactions themselves, not by the module under test.
  3. Failures can be replayed. Anything random is driven by a recorded seed.
  4. Nothing is "done" on a claim. A milestone is finished when its tests pass in the automated checks.

The simulator

The main safety net. It is possible because the core does no input or output.

  • Schedules: a seeded generator picks operations for every party: join, pay, receive, change liquidity, update a layer, rotate, close, exit.
  • Network faults: each message may be dropped, delayed, duplicated or reordered.
  • Crashes: each party may be stopped at every point where it saves or sends, and restarted from what it saved.
  • Cheating: scripted dishonest hosts and members try each attack in the threat list: paying a close to themselves, shrinking a balance, publishing an old state, sending a bad partial signature, withholding a result, altering a nonce.
  • After every step, the invariants below are checked.
  • On failure, the seed and schedule are saved so the case becomes a permanent test.
Invariants

Checked after every simulator step and at the end of every regtest scenario.

  1. Money is conserved across every state change.
  2. Every member can leave alone with at least what they are owed.
  3. No party signs two different states with the same number.
  4. Nothing is sent before it is saved.
  5. No secret nonce survives a restart or is used twice.
  6. No party's software publishes a state it has cancelled.
  7. Every payment deadline is later than the time needed to exit.
  8. The host's funding is never signed before every exit is signed.
  9. An honest party is never named as the cause of a failed signing round.
Regtest scenarios

Each runs through a Bitcoin node and again through an Electrum server.

  • Lobby fills to target; lobby starts at the deadline; lobby misses its minimum.
  • Join, receive, pay inside the factory, pay out through the host's Lightning node, receive from outside.
  • Liquidity change; layer update; rotation into a new factory; cooperative close.
  • A member exits alone with the host gone, through to spendable coins.
  • The host publishes an old state; a member publishes an old state.
  • Restart of each program in the middle of each operation.
  • A member away for the whole response window.
  • Restore from backup, then recover without publishing.
Sizes

Routine runs use 4, 8 and 32 members. Nightly runs use 128 and 256. Release candidates run the target of 512.

Tooling
  • Automated checks on every push: a normal build and a build with memory-error and undefined-behaviour checkers. In place now.
  • To add as code arrives: fuzzing of every message decoder with a kept corpus; a thread-error checker for anything concurrent; coverage reports; a nightly job for the long runs.
  • Compiler warnings are errors.
Before a release candidate
  • Every invariant has passing tests at all three of simulator, regtest and signet.
  • Every safety rule has its rule-removed test.
  • The long simulator run and the fuzzers have run clean for a day.
  • Nightly scenarios have been green for seven nights.
  • Each engine has had an independent review, and its findings are closed or recorded as accepted.
  • The documents state what is unreviewed.

Outside review then begins; the owner arranges it.

SuperScalar Improvement Proposals (SIPs) · docs/sips/README.md

How changes to rules and behaviour are requested, discussed and decided. Modelled on the processes Bitcoin (BIPs) and Lightning (bLIPs) use.

SIPs are meant for anyone building SuperScalar factory software, not only Gazpacho. They live in this repository for now and can move to a home of their own.

Why

New joining rules, safety rules and protocol features usually change the code that decides what is safe to sign. Such changes are made in the open, one at a time, with a written record of who agreed and who objected. The record is kept even for proposals that are never shipped.

What needs a SIP
  • Anything that changes what a member or host will sign, or refuse to sign.

  • New rule profiles, joining requirements, deposits, reputation schemes.

Status Meaning
Draft Written up using a template; not yet under discussion
Discussion Open for comment. Reviewers reply with ACK (agree), NACK (object, with reasons) or a request for changes

The rule in one sentence

A host may open a lobby that starts at once when it reaches a target size, starts at a deadline if it has reached a minimum size, and is cancelled at the deadline otherwise.

Who sets it and who checks it
Set by Host
Where it is published Lobby listing and host's terms
Checked by Host's software starts the lobby; each member's software checks the size against the member's own conditions
Checked when Continuously while the lobby is open, and again at signing
Settings
Name Type Range Default Meaning
target_members count 2 to the host's maximum 50 Reaching this starts the lobby immediately
minimum_members count 2 to target_members 30 Fewer than this at the deadline and the lobby does not start
deadline time 3 hours after opening When the lobby starts or is cancelled
on_shortfall choice cancel, or carry members over to the host's next lobby cancel What happens below the minimum
What it needs to know
  • How many members are seated and whose software is connected and ready. The host knows this directly; a member is told by the host and cannot verify the count until signing.
  • Each member's own minimum, held by that member's software.
Effect on what is safe to sign

At signing, a member's software counts the members in the tree it is asked to sign. It refuses if the count is below the host's published minimum or below the member's own. So a host cannot start a smaller factory than promised without every member's software noticing.

Why it is wanted

A factory's on-chain cost is shared among its members, so a host needs enough of them to make it worthwhile, and members want to know they are not joining an empty factory. A deadline lets everyone plan.

How it could be abused
  • A host inflates the count to attract members. Limit: the true count is visible in the tree at signing, and members' software refuses a short tree.
  • Fake members fill a lobby to trigger an early start and then do not sign. Limit: non-signers are removed and the round reruns; if the count falls below the minimum the lobby does not start. This wastes time, not money.
  • A member holds a seat and never readies. Limit: only connected, ready members count toward the start.
Who it shuts out

Nobody. A host that wants no minimum sets it to 2.

Privacy

The target, minimum and deadline are public in the listing. The live count is given by the host on request.

Tests
  • Lobby reaches the target before the deadline: starts immediately.
  • Lobby is between minimum and target at the deadline: starts.
  • Lobby is below the minimum at the deadline: cancelled, or carried over, as set.
  • Members drop during signing and the count falls below the minimum: does not start.
  • With the member-side count check removed, a host starting a short tree goes undetected; the test for this must then fail.

Hand-off to SuperScalar

Findings and requests for the SuperScalar repository.

Hand-off to the SuperScalar repo session · docs/handoff/2026-11-11-to-superscalar.md

From the Gazpacho session, 2026-11-11. Gazpacho imports SuperScalar's low-level files unchanged and builds a wallet on top. A trial run and an import study produced one bug report and three requests.

Tested at 2cebbdf plus the start-up crash fix (b812be3, 292fbe1), Release build, regtest, 4 clients, default pseudo-Spilman leaves, --amount 1000000.

1. Bug: a client cannot complete a unilateral exit

Steps: create the factory, make payments, kill the LSP, run the client with --force-close repeatedly while mining blocks.

Result: all 14 tree transactions confirm, then the client's commitment transaction is rejected on every attempt:

min relay fee not met, 154 < 167

The fee appears to be computed for a 154-vbyte transaction while the transaction is 167 vbytes. --test-full-settlement fails the same way on all four channels, including with --fee-rate 2000. So a client never reaches a spendable output without the LSP.

Also seen: the default --amount 100000 cannot run a payment, because the per-side balance (5788 sats) is barely above the 5000-sat reserve.

2. Request: let the caller supply randomness

These files read the operating system's random source directly:

  • musig.c:9 (every signing nonce)
  • factory.c:3687
  • bip39.c:171
  • keyfile.c:60, keyfile.c:167
  • wallet_source_hd.c:244
  • invoice.c:27

Gazpacho's core is handed all randomness by the program around it, so that a whole factory can be simulated repeatably from a seed. A callback or context parameter, defaulting to today's behaviour, would let us use these files unchanged.

3. Request: no direct output or environment access in the tree builder
  • About 45 fprintf(stderr, ...) calls in factory.c.
  • A getenv debug hook at factory.c:2122.
  • A test-only global at factory.c:2290.

A log callback, and moving the test hooks behind a build flag, would do.

4. Request: a defined rule for participant order

Tree transaction IDs depend on each participant's slot, and slot order today is the order in which clients connect. Two parties can only build the same tree if they are told the order. Either a canonical rule (for example, sorted by public key) or an explicit order carried in the proposal and checked by every client would remove the dependence on connection timing.

5. Finding: tree order can depend on the C library's sort

factory_init_from_pubkeys and factory_init set placement_mode = PLACEMENT_TIMEZONE_CLUSTER (factory.c:888, :830). factory_build_tree then sorts the clients with cmp_timezone_cluster (factory.c:24-35). profiles[] is zero-filled by default, so every comparison returns 0 and the result depends on how qsort orders equal elements, which the C standard leaves open. On glibc 2.39 the order comes out as 1..N. On another C library two honest parties could build different trees.

Suggested: default to PLACEMENT_SEQUENTIAL, or add a final tie-break on participant index in the comparison.

6. Finding: partial signatures are never verified individually

musig_verify_partial_sig exists (musig.c:423) but has no caller. factory_session_set_partial_sig stores each partial signature unchecked, and factory_session_complete_node aggregates without checking. Only the final aggregate is verified (factory_verify_all). A bad partial signature is therefore detected only as a failed aggregate, with no way to tell who sent it.

1. Relationship to the SuperScalar repo
  • Gazpacho is its own codebase.
  • It imports SuperScalar's primitives as a pinned snapshot under core/superscalar/: tree builder, MuSig2 sessions, timelock counter, ladder, transaction and script builders, adaptor signatures, key handling. About 11,000 lines. (proposed: vendored snapshot, not a live dependency)
  • Changes to imported files go to the SuperScalar repo first, then we update the snapshot. No private forks of the primitives, except a clearly listed patch queue when we cannot wait.
  • Everything above the primitives is written new, using SuperScalar's host and member code as the reference for behaviour.
  • A differential test builds the same factory in both and requires identical transaction IDs.

3. Core contract

One entry point: an event goes in, a list of actions comes out. The core never blocks and never calls the outside world.

  • Events: message received, timer fired, chain event, user command, storage confirmed.
  • Actions: save records (one atomic batch), send message, broadcast transaction, watch script, set timer, tell the user.
  • Save before send: the shell runs an action list in order and does not send anything until the batch before it is safely stored. This is enforced once, in the shell runner, for every engine.
4. Engines
  • Signing round engine. One state machine for every group signature: propose, nonces, partial signatures, done. SuperScalar has about 40 message types across seven separate families for this (create, close, leaf advance, path, state advance, sub-factory, reallocation). Here it is one engine, given "what is being signed" and an acceptance rule.
  • Acceptance rule (member side). Before contributing to any signature a member computes, from its own data only: "after this, can I still exit alone with at least what I am owed?" If not, it refuses. This single rule replaces per-ceremony checks.
  • Channel engine. One update routine: save new state, send signature, receive and verify revocation, save, release own secret. Handles reconnect and updates that arrive mid-update by queueing, never dropping.
  • Payment engine. Invoices, incoming and outgoing payments, deadlines derived from the tree's exit time.
  • Exit engine. Plans a unilateral exit: which transactions, in what order, when each becomes valid, and how fees are bumped from the on-chain wallet.
  • Watch engine. Lists what must be watched and what to do when each thing appears on chain.
5. Decisions on behaviour
  • Sign before fund: the host signs its funding transaction only after the whole tree and every member's exit are signed. Built in from the first version.
  • One funder per factory (the host). Members start at zero; pay in over Lightning or swap in.
  • Pseudo-Spilman leaves, one member per leaf. Payments never change the tree; only liquidity changes do.
  • Payment deadlines are computed from the factory's exit time plus a margin. Payments with less headroom are refused.
  • Members exit automatically before the factory's expiry if the host has not rotated them.
  • Host terms are a published record; the member's limits are checked before any signing.
6. Message format **(proposed, revised 2026-11-11)**

Do not invent a format. Speak Lightning's own wire language, so a Gazpacho connection is an ordinary Lightning peer connection that also carries factory messages.

  • Connection: the BOLT 8 encrypted transport (Noise XK, the responder's key known in advance, which is exactly a pinned host key). Over TCP, and over WebSocket binary frames for browsers.
  • Framing: the BOLT 1 message: 2-byte type, payload, optional trailing fields. Maximum 65,535 bytes.
  • Session: the standard init (feature bits, chain), ping/pong, error and warning.
  • Extending without breaking: no version numbers. Feature bits say what each side supports; every message ends in a typed-field (TLV) stream; unknown odd fields and messages are ignored, unknown even ones are refused ("it's ok to be odd").
  • Factory messages: one odd message type in the custom range (32768 and above), carrying an envelope in the style of bLIP-56: protocol name, factory identifier, sub-message kind, then typed fields. About 15 sub-message kinds.
  • Channel messages: the standard BOLT 2 set (update_add_htlc, commitment_signed, revoke_and_ack, channel_reestablish, stfu), with the taproot-channel fields for signing nonces. Reconnect follows channel_reestablish, which is the most-reviewed part of Lightning.
  • Large data: group-signing data for hundreds of members exceeds one message. Send it as a sequence of small messages with an explicit "complete" marker, as Lightning's interactive transaction building does.
  • Member backup at the host: the standard peer storage messages (peer_storage, peer_storage_retrieval).
  • Host terms and service requests: binary typed fields in the first release; an LSPS-style (bLIP-50) interface can be added later for wallets that already speak it.
  • How it is written: message tables in spec/, in the same table form the BOLTs use. Encoders and decoders are generated from the tables, not written by hand. Every message has test vectors, and every decoder is fuzzed.
  • The specification is offered to the SuperScalar repo as the shared format, and written so it could be submitted as a bLIP.
7. Storage
  • An append-only journal of typed records plus periodic snapshots.
  • Encrypted at rest.
  • The same journal, encrypted, is the off-device backup. The host also holds an opaque copy for the member.
8. Chain port
  • Subscribe to a script; get a transaction's confirmation with proof; broadcast; fee estimate; chain tip.
  • Block headers are checked for proof of work, and confirmations are checked against headers, so a server cannot invent a confirmation. It can only hide one, which asking several servers addresses.
  • Backends: Electrum protocol, HTTP block explorer, Bitcoin node.
9. Testing
  1. Vectors and differential tests: official cryptographic vectors; identical transaction IDs to SuperScalar.
  2. Engine unit tests.
  3. Simulator: host, N members, a simulated chain and a simulated network in one process, driven by a seed. It drops, delays and reorders messages, crashes any party at every save point, and plays scripted cheating peers. Invariants are checked after every step. This is the main safety net and is only possible because the core does no I/O.
  4. Regtest end to end: the real programs against a real Bitcoin node and Electrum server. Scenarios: join, pay, receive, swap in, liquidity change, rotation, cooperative close, forced exit, host disappears, host publishes an old state, member publishes an old state, restart in the middle of each ceremony.
  5. Signet and testnet: the public host with scripted users running nightly.
  6. Always: sanitizers, fuzzing of every message parser, and for each safety rule a run with the rule removed that must fail.

Invariants checked everywhere

  • Money is conserved across every state change.
  • Every member can exit alone with at least what they are owed, at every step.
  • No party signs two different states with the same number.
  • Nothing is sent before it is saved.
  • No party's software broadcasts a state it has revoked.
  • Every payment deadline is later than the time needed to exit.
  • The host's funding is never signed before every exit is signed.

14. Decisions from review 1 (owner's answers, 2026-11-11)
  1. Tree: the first release ships the full layered tree. Build order is fixed tree first, then the layers; the core is designed for the full tree from the start.

Lobby: first sketch (to be developed)

  • A host publishes a lobby: terms, minimum and maximum members, start rule, closing time. The listing and the host's proof of funds or channels are on Nostr; everything else is direct.
  • A member's app checks the terms against the member's limits before showing "join".
  • Joining is a direct connection to the host. The member appears in the lobby and can mark themselves ready.
  • Changing the rules: the host proposes new terms; each member accepts or leaves. There is no binding vote, because nothing binds anyone until they sign, and every member signs for themselves.
  • Start rule: minimum reached, and either all present are ready, or the host starts, or the closing time arrives.
  • At start, members who do not answer are dropped and the signing round restarts without them.
  • Open: a small refundable deposit to deter people who join and never sign; how much of the lobby state is public.

Host's Lightning node: the adapter interface

Four operations are enough:

  1. Pay an invoice, with a spending limit and a deadline; report the payment secret on success.
  2. Create an invoice for a payment hash whose secret the node does not know, and hold the incoming payment open.
  3. Settle a held payment once the member has revealed the secret.
  4. Cancel a held payment.

LND offers all four natively. Core Lightning offers 1 natively and needs a plugin for 2–4.

16. M0 findings: what the reference code does today (2026-11-11)

From a trial run of SuperScalar (main plus its start-up crash fix) on regtest with four members and the default leaf type.

What works

  • Factory creation, four payments and a cooperative close ran correctly; final balances matched to the satoshi. Creation took about 2 seconds, each payment about 2 seconds.
  • A host-side forced close published and confirmed all 14 tree transactions.

What does not

  • A member exiting alone, with the host gone, got all 14 tree transactions confirmed but could not publish its channel transaction: the fee built into it is below the relay minimum (154 against 167). So in the reference code today a member cannot complete an exit without the host. Gazpacho's channel engine replaces this code; the finding is passed to the SuperScalar repo.
  • The default factory size is too small to make a payment (channel reserve exceeds the balance).

Foundations: separable

  • 16 of the 20 candidate files build and run alone, needing only the signature library and a general cryptography library: tree, group signing, timelock counter, ladder, transaction and script builders, adaptor signatures, key derivation, recovery phrases, address and invoice encoding, fee helpers.
  • 4 files are tied to the old database or channel code and are not imported as they are: keyfile, invoice, sweeper, on-chain wallet source. Gazpacho writes its own.

Changes the imported files need before they fit the core's rules

  • Randomness is read directly from the operating system in several places, including for every signing nonce. The core must be handed randomness by the program around it.
  • Diagnostic printing, one environment-variable hook and one test-only global variable in the tree builder.
  • Member positions in the tree follow connection order, not key order, and the transaction IDs depend on it. Gazpacho must fix the order by an explicit rule.

Message counts observed

17. Third discussion (2026-11-11)
  • Voting and vote-to-remove are off for now (owner). The lobby uses host removal, personal block lists and locally kept history. See LOBBY.md.
  • No threshold key for the factory. A key that a majority can use without the minority would let that majority spend a member's money. The factory stays "everyone signs". Threshold keys are fine where one party splits its own key.
  • Removing someone from a live factory can only mean they agree to leave or their branch is published; either way they keep their money. Anything needing every signature can be stopped by one member, so the design limits how often everyone is needed rather than voting.
  • Identity and joining requirements (control of coins, signing history, a chosen identity) will develop over time and must remain options a host sets. New joining rules usually need balances, coins or other state to decide what is safe to sign, so adding one is normally a reviewed change to the safe-to-sign module itself, which is kept small, with defined inputs and its own tests (owner's correction).
  • Coordination as its own library. The lobby, the signing round engine and the proof-of-fault scheme are written without dependence on the factory code so they can be split out.
  • Host nodes are listed with difficulty in HOST-NODES.md. LND first.
  • A member adding coins to their own leaf (later feature): other members never sign anything involving it, and nothing above that leaf changes, so their exits and balances are unaffected. The added coins sit in a separate on-chain output under joint control of that member and the host, so a cooperative close or rotation must spend that output in the same transaction that pays the member. 19. Decisions from questions round 2 (2026-11-11)

Lobby

  • Timing. One mechanism with timers the host sets. Gathering is long: a lobby can stay open for hours or days and members can join at any time and leave their app to act for them. Signing itself is short and happens at the scheduled start. Reason: the secrets used in a signing round are never stored, so every member's app must stay running from the first signing step to the second, and anyone dropping out forces a restart for all. A short signing window keeps that cheap; a long gathering window gives the convenience. A host may lengthen the signing timers if it accepts more restarts.
  • Audience. Newcomers with no funds are the main audience. Each host sets the share of seats they may take.
  • Visibility and admission are two separate settings. A lobby is listed on Nostr or unlisted; and open to anyone or by invitation. Invitations are links, shown as QR codes. An unlisted, invitation-only lobby gives privacy in practice.
  • Deposits: not in the first release. Planned as the next step after it (issue 3).
  • Names, chat and rule-change requests are each a setting the host can switch off. With all three off, members see only a head-count.
  • Optional self-identification. A member may attach an identity to their seat. Standard kinds are proven by signing the lobby's challenge with that identity's key (a Nostr key, a Lightning node key). A free-text field is allowed and always shown as unverified.
  • Identity is new for each lobby by default; a member may choose to bring a lasting one.
  • What is on Nostr. A listing carries the terms the host has fixed and the acceptable range for the others, size limits, start time and an expiry. It changes rarely. Live details, such as how full a lobby is, are asked of the host directly.
  • Track records. A host may publish the factories it has funded. Whether members can likewise prove past participation by signing with keys or coins from earlier factories is to be investigated (it links a member's factories together, so it must be opt-in).
  • Profiles: all four ship: Safety, Standard, Starter, Circle.

Product

  • Chain servers: well-known public servers at first; one of our own is added around launch.
  • Reminders: countdowns in the app first; then Nostr messages, email, and phone notifications with the mobile app. Ways to act while the member is away are collected in AWAY.md.
  • The repository goes public now (owner's decision), with SECURITY.md and CONTRIBUTING.md added first.

How we work

  • New rules and features follow a proposal process modelled on BIPs and bLIPs: request in a set format, open discussion, ACK or NACK on record, then a separate decision on whether it ships. A proposal can be approved and not shipped, with the reason stated, so other factory software can adopt it. See sips/.
  • Review: independent AI review of every engine as it is built, by several different models; and before real funds, outside human reviewers, including people who try to break it. The owner arranges outside reviewers.
  • Hand-off notes are local documents; the owner pastes a short message pointing the other session to them.
20. Lobby start rule and SIPs (2026-11-11)

Soup wallet's design had the same rule (min_clients_to_start, a force-start deadline, immediate start when full) and re-opened on a shortfall; here carry-over to the next lobby is an option and cancelling is the default.   • Proposals are SIPs: SuperScalar Improvement Proposals, in sips/, with categories Rule, Protocol, Process and Informational, a rule-request template and a worked example.

Lobby research

Background: how comparable systems gather people and handle those who stall, with sources.

Lobby: research and design note · docs/LOBBY-research.md

Research note, 2026-11-11. Status: proposal for the owner's decision. Nothing here is decided.

The lobby is the waiting room where a host and members gather before they jointly sign a new factory. This note reports what earlier work and comparable systems did, recommends a design, and lists what is uncertain.

The note has three clearly separated parts:

  • Part A is what was found in sources, with links.
  • Part B is the recommended design. It answers the ten questions in order.
  • Part C is what is uncertain or unverified, and the questions that need the owner.

Terms used throughout:

Term Meaning
Host The party that funds the factory. The design literature calls it the LSP.
Member A party that gets a channel in the factory. The literature calls it a client.
Terms record The structured record a host publishes: tree shape, sizes, lifetime, fees, limits.
Limits The member's own conditions, held in the member's wallet.
Seat One member's place in a lobby, identified by a public key the member chose for this lobby.
Roster The list of seats that will be in the tree.
Signing attempt One run of the group signing: propose the tree, collect nonces, collect partial signatures, combine.
Partial signature One signer's contribution to a MuSig2 group signature. It is not a valid signature by itself.
Sybil One person operating many identities that look like separate people.
Summary
  1. Before signing completes nobody has money at risk. Every defence in the lobby is therefore a defence against wasted time, not against theft. The defences should be light in proportion.
  2. The only real guarantee for a member is the check their own wallet makes on the actual tree at signing time. Everything said in the lobby is a convenience that lets the wallet leave early. This is sound and is the centre of the design.
  3. Votes cannot bind anyone, because every participant signs for themselves and the host chooses who is in the tree. A "vote" can only be a structured way for members to state preferences so that the host can pick a value most members will accept. Vote-kick has the same limit, and in a lobby where identities are free it can be captured by one person with many identities.
  4. Every comparable system that successfully bans misbehaving participants bans a scarce resource (a coin, a paid fee, a locked bond), never an identity. Gazpacho members arrive with no funds, so there is no scarce resource unless the design adds one. This is the hardest problem in the note.
  5. Only one kind of misbehaviour is provable to outsiders: a bad partial signature, and only if every signing message is signed with the sender's seat key. A participant who simply does not answer can never be proven guilty, because the host could have dropped the message.
  6. Recommended first version: listing on Nostr, direct join, versioned terms with automatic leave, a scheduled start with a ready check, signed signing messages, drop-and-restart up to three attempts, host kick plus a personal block list, local-only reputation, no deposit. Add a short held Lightning deposit at the ready check second.

A3. Coinjoin coordination

Coinjoin is the closest precedent: many strangers must all sign one transaction, and one non-signer spoils the round.

Wasabi (WabiSabi). Sources: user documentation, coordinator defaults, ban logic.

Item Value
Phases Input registration, connection confirmation, output registration, signing, broadcast
Start rule Start when the maximum number of inputs is reached, or when the registration timer ends and the minimum is met
Timers Registration 1 hour; confirmation, output registration and signing 1 minute each
Size Maximum 100 inputs, minimum 50

Why it works: each disruption attempt ties up a real coin, and a fresh coin costs an on-chain transaction. Criticism: Peter Todd on the bitcoin-dev list, June 2022 pointed out that the only answer to a dropout is punishment in later rounds, and that an attacker with many coins can still disrupt. No published measurement of the cost of disruption was found.

JoinMarket fidelity bonds. Sources: design, documentation. A fidelity bond is a coin locked until a future date so that an identity is costly to create. Nobody can seize it; the cost is the time value of the locked money. Bond value grows faster than linearly with the amount (exponent 1.3), which rewards one large bond over many small ones. Counterparties are picked at random weighted by bond value, and 12.5% of picks ignore bonds so that newcomers are not shut out. Limits: the bond is public and links to the owner's coins; a long-term holder gets a bond almost for free; the unbonded picks are cheap to fake.

Whirlpool. Sources: archived server repository and theory document. Five participants per mix. Each participant pays the coordinator's fee once, in advance, in a preparatory transaction; that fee is the Sybil cost. Phases of about one minute. The theory document rejects both IP bans and fidelity bonds and bans misbehaving coins instead. Production ban values could not be verified.

A4. Ark and similar round protocols

Sources: arkd settings, arkd offence list, Second: rounds, Second: hArk, Delving post on Ark with new opcodes.

  • Ark has the same structure as a factory creation: the operator and all round participants sign a tree with MuSig2.
  • Rounds are on a fixed timer (Second: hourly; arkd: a session of 30 seconds, schedulable). Wallets must be online in the window.
  • arkd records named offences: nonce not submitted, signature not submitted, invalid signature. Three offences bring a five-minute ban. The ban again attaches to a resource (the participant's existing balance in the system), not an identity.
  • The direction of development is to remove steps that need everyone at once. Second's hArk moved one all-must-sign step out of the round because "one user's failure" stalled everyone. Delegated signers can sign the tree on behalf of offline phones.
A5. Finding the culprit in a failed group signature

Sources: BIP-327 (MuSig2), RFC 9591 (FROST), ROAST, ChillDKG.

  • BIP-327 lets whoever collects the partial signatures check each one individually and identify exactly one signer who sent a bad one. It calls this identifiable aborts. It holds only if messages were not tampered with (authenticated connections), the nonces were combined honestly, and every partial signature was checked.
  • BIP-327 warns that a dishonest collector "can always make signing abort and wrongly hold honest signers accountable".
  • BIP-327 also notes that partial signatures can be forged by anyone. A bad partial signature shown to an outsider therefore proves nothing unless its author also signed it with an identity key.
  • A signer who does not answer is not covered at all. Nothing in MuSig2 or FROST makes silence attributable.
  • A nonce must never be used for two signing runs, or the signer's key leaks. Every restart needs fresh nonces.
  • ROAST makes threshold signing robust by opening new sessions with whoever responds. It relies on spare signers. In an all-must-sign scheme there are none: removing a signer changes the key, which for a factory means a new tree. Only the pattern "identify, remove, rebuild" carries over.
  • ChillDKG is the closest example of signed transcripts. It states plainly that there is "in general, no way to verify an accusation by some party that another party is to blame".
A6. Lightning: griefing, jamming and held payments
  • Dual-funded channels (BOLT 2): a peer can stall the joint construction and keep the other side's coins reserved. The specification's advice is not to treat reserved coins as locked and to reuse them across sessions. This applies directly to a host's reserved funding.
  • Liquidity advertisements (proposal): the seller "should keep the channel open for at least a month, but there is no way to guarantee that"; the buyer's remedy is to stop using that seller. An enforced lock was dropped because it could be used to pin the seller's funds.
  • Channel jamming (overview, Unjamming Lightning): the researched answer is two parts used together, a small unconditional fee and locally kept reputation. After several years, the reputation part exists in logging-only form (LND, October 2026) and upfront fees are deployed nowhere. The lesson is that purely local reputation is what proved shippable.
  • Held payments (overview): the receiver accepts a payment but delays completing it, then either completes or cancels. While it is held, every routing node on the path has liquidity and one payment slot locked without compensation. If it is held close to its expiry, channels along the path are force-closed. Consumer wallets refuse long holds: Phoenix rejected RoboSats bonds once the hold window grew to two days.
  • RoboSats bonds (documentation): a held payment of about 3% of the trade to the coordinator, cancelled on success and completed on forfeiture. Whoever created the payment secret can complete the payment at any time, so the bond is fully trusted to the coordinator.
  • Proving coin ownership as an entry ticket: BIP-322 defines a signed proof of funds. aut-ct proves ownership of some coin without revealing which, one token per coin per context; its author calls it experimental and unsafe.
A7. Game lobbies
  • Ready checks. League of Legends escalates penalties for leaving at the ready stage: 6 minutes, 30 minutes, 12 hours, with the level decaying after a clean day. The penalty is a delay before the next attempt, attached to an account that is costly to replace.
  • Vote-kick. World of Warcraft's group finder: majority vote; the initiator must give a reason; no kick in the first 15 minutes or during a fight; at most two kicks per group; players who initiate kicks often are blocked from initiating for two hours.
  • Known abuse: a group of friends that forms the majority kicks the lone stranger. Counter-Strike 2 reportedly made a solo player matched with a party of four immune to kicks (secondary source only).

The safeguards are thresholds, cooldowns, limits per group and immunity for the outnumbered. All of them assume that an account is costly to replace. None of them survives free identities.

A9. The pattern across all sources
  1. Bans work only on scarce things. Wasabi bans coins, Ark bans existing balances, Whirlpool charges in advance, JoinMarket prices identities with locked coins, RoboSats holds a bond, games rely on accounts with history. No system was found that successfully polices free identities.
  2. Short signing windows and an automatic rerun without the non-signers is the standard liveness pattern (Wasabi, Whirlpool, Ark, and the SuperScalar notes).
  3. Penalties escalate with repetition and decay with time.
  4. Reputation that shipped is local. Shared reputation is either per coordinator or absent.
  5. Nobody proves blame for silence. Systems exclude locally and move on.

Part B. Recommendations

B0. Three facts that shape everything

Fact 1. Nothing binds until a participant signs. The host decides which seats are in the tree. Each member decides whether to sign. No message, vote or promise in the lobby changes either of those.

Fact 2. Identities are free. A seat key, a Lightning node key and a Nostr key each cost nothing to create. Any rule that counts identities can be captured by one person.

Fact 3. The damage a griefer can do is bounded and small. Members have no funds in play. The host's funding is only reserved, not spent, until the tree is signed, and reserved funds can be released at once. The loss is everyone's time and the host's opportunity.

B1. Lobby state machine (question 1)

Lobby states

A member's seat states

Requested, then Seated (the host admitted the member), then Accepted (the member's wallet accepted the current terms version), then Confirmed (answered the ready check), then Signed, then Member. A seat can end at any point as Left (member's choice), Removed (host's choice, or automatic after a fault) or Declined (the wallet refused new terms).

Start rule

The host publishes the start rule as part of the lobby rules. Recommended form:

  • A scheduled start time, published when the lobby opens. A fixed time is the best tool for getting phones online together and matches the daily schedule in the SuperScalar design.
  • A minimum and a maximum number of members.
  • A closing time after which the lobby is cancelled if it has not started.
  • Optional start when full: if every seat is Accepted before the scheduled time, give two minutes' notice and start.

At the scheduled time: if the number of Accepted seats is at least the minimum, go to Ready check. If not, move the start to the next scheduled slot (the host states the slot spacing in advance) or cancel at the closing time. The lobby never starts below the minimum.

The host can always cancel. Nothing can prevent that, because the host can simply refuse to sign. The host cannot start early in any way that matters, because each member's wallet checks the tree (B2).

Timers (proposed defaults, to be tuned on signet)

Timer Default Basis
Ready check window 60 seconds Wasabi's one-minute phases; prior work's 30-second heartbeat
Nonce window, per attempt 30 seconds Software answers without user action
Partial signature window, per attempt 30 seconds Same

What happens in each attempt

  1. Propose. The host sends each confirmed member the roster, the tree, the funding transaction (unsigned) and the attempt number.
  2. Member check. Each wallet runs the full check in B2. A wallet that refuses says so with a reason code and leaves.
  3. Nonces. Each member sends fresh nonces, signed with their seat key.
  4. Nonce set. The host sends everyone the full set of signed nonces.
  5. Partial signatures. Each member sends partial signatures, signed with their seat key together with a hash of the nonce set they used.
  6. Verify and combine. The host checks each partial signature as it arrives and combines them.
  7. Complete. The host sends the finished signatures. Each wallet verifies every signature on its own exit path before it treats the factory as real.

No-shows and restarts

  • A member who misses a window, or whose partial signature fails verification, is removed.
  • All members who missed the same window are removed together, not one per attempt.
  • The next attempt includes only members who behaved in the previous one, plus standby seats (below). No new joiners. This is Wasabi's blame round.
  • Before each new attempt every wallet re-runs its check, because the tree and the member count have changed.
  • If the remaining members fall below the minimum, the lobby returns to Open with the next scheduled start. It does not start short.
  • After three failed attempts or ten minutes, the lobby returns to Open (or is cancelled at closing time). Members who caused failures are not readmitted to that lobby.
  • Every attempt uses fresh nonces and a new session identifier. Nonces are never stored.

Standby seats. The host may admit a few more members than the maximum. Extra members pass the same ready check and wait. When a member is removed, a standby member takes the place in the next attempt, so one failure does not shrink the factory. This is the "backfill" idea from game matchmaking.

Limit. An attacker holding k seats can respond with all but one each time and burn k attempts. The attempt cap, the limit on unproven seats (B5) and standby seats bound this; nothing removes it.

What a member's wallet checks at each step

Step Check
Reading the listing The listing is signed by the host's key, not expired, and the host has a vouch from a coordinator the user accepts. The public terms pass the member's limits. If not, the lobby is not offered.

B2. Member-locked conditions (question 2)

Where the guarantee comes from

The guarantee is one sentence: the member's wallet signs nothing until the tree in front of it passes every condition the member has set, computed by the wallet from the proposal itself. This is already the member-side acceptance rule in DESIGN.md §4. It does not depend on the lobby, the host, other members or any vote.

The lobby adds convenience only. Checking the published terms lets the wallet avoid lobbies that will fail the check, and leave early when a rule change makes failure certain.

"Locked in" should therefore mean three concrete things:

  1. The member's conditions are stored in the member's wallet and bound to the seat when the member joins.
  2. Nothing the host or other members send can loosen them. Only the user can, by an explicit action in their own wallet.
  3. At every later step (terms change, ready check, each signing attempt) the wallet re-evaluates them and leaves on failure.

With this, "nobody is carried into a factory that violates their conditions" holds for honest wallet software regardless of what the host or the other members do.

Which conditions can really be locked

Not every condition is equally checkable. Reusing the prior work's classification:

Kind of condition Examples How it is enforced Strength
Visible in the signed tree Channel size, factory lifetime, exit delays, tree shape, depth of the member's exit path, number of leaves The wallet computes it from the proposal Full
Enforced by the wallet later Fee per liquidity purchase, payment size limits, how often the host may ask for re-signing The wallet refuses each later request that exceeds the limit Full, as long as the wallet keeps checking
A promise about host behaviour "The host will offer a place in the next factory", "the host will stay online", forwarding fees charged outside the factory Nothing None. The wallet can only record the signed promise.

The wallet's settings screen should show which kind each condition is, so that a user does not believe a promise is a guarantee. The host should sign its terms record with its host key, so that a broken promise can at least be shown to others later.

Two conditions that are weaker than they sound

"At least 10 members." The wallet can verify that the tree has at least 10 member leaves. It cannot verify that they are 10 different people. The host, or anyone, can fill seats with puppets, as ZmnSCPxj also notes. The condition should be described to users as "at least 10 seats". It is also worth asking what the member wants from it: a larger tree means a deeper and more expensive exit path for each member, so a larger count is not simply better for the member.

"Fees below some level." A fee the member pays is enforceable, because the wallet refuses to pay more. A fee the host deducts on some future service the member has not yet asked for is a promise.

Should the host see a member's conditions?

Recommendation: no, by default. The host learns only "accepted" or "declined, reason code". If the host saw every member's maximum fee it could price exactly at each member's limit. The one deliberate exception is the preference ballot in B3, which a member may choose to fill in.

B3. Voting on open rules (question 3)

What voting can and cannot mean

A vote in a lobby cannot be binding in either direction.

  • It cannot bind a member, because the member's wallet will not sign a tree that fails the member's conditions (B2).
  • It cannot bind the host, because the host builds the tree and can decline to.
  • It cannot be made fair by counting, because one person can hold many seats.

What remains is useful but modest: a structured way for members to tell the host what they would accept, so the host can pick the value that keeps the most members. The note recommends calling this "preferences" in the user interface and reserving "vote" for the informal description.

Recommended design

  1. The host marks each rule as fixed or open. An open rule has a range the host will tolerate.
  2. Most choices should be per member, not shared. Channel size, inbound liquidity and which optional features a member uses can be chosen by each member within the host's range, with no vote at all. Only rules that are truly shared need preferences: start time, factory lifetime, tree shape, minimum and maximum size, and the profile.
  3. Each member's wallet sends a ballot for each open shared rule: the range the member would accept, and optionally the value the member prefers. The acceptable range is taken from the member's limits, and the member chooses whether to disclose it.
  4. The host's software chooses the value inside its own range that the largest number of seated members accept. Ties are broken by the median of the preferred values. The median is used rather than the average because a minority cannot drag a median by stating extreme values.
  5. The result is issued as a new terms version. Every wallet re-evaluates as in B2. Members whose conditions it fails leave. Nobody is forced.
  6. Ballots are signed with seat keys and the host shows the set of ballots to members on request, so that members can check the host followed its stated rule.

Weighting

Recommended: one ballot per seat, counted only for seats that have passed whatever admission cost the lobby uses (B5). No weighting by size of channel or by reputation in the first version.

The honest position on weighting: because identities are free, any weighting scheme is only as good as the cost of a seat. Where seats are free, the count means little, and the host should treat the result as advice. The host is entitled to weigh ballots however it likes, since it decides anyway; what the design can require is that the host states its rule in advance and can be seen to follow it.

Limits

  • A person with many seats can move the result, within the host's range. The effect on an honest member is that the outcome falls outside their conditions and their wallet leaves. They lose time, not money.
  • The host can ignore the ballots. A member who dislikes that leaves.
  • The audit in step 6 proves the host counted the ballots it showed. It cannot prove the seats were real people.
B4. Vote-kick (question 4)

Can it be made safe against many fake seats?

Not by counting seats. If seats are free, one person can hold the majority and can both kick honest members and protect a griefer. The safeguards used by games (thresholds, cooldowns, immunity for the outnumbered) all assume an account is costly to replace. A vote-kick is exactly as Sybil-resistant as the cost of a seat, and no more.

There is a second, less obvious problem. Members have little to base a kick on. For privacy, a seat key should be new for each lobby, so members cannot recognise each other from earlier lobbies. There is no chat. The only behaviour visible in a lobby is whether a seat signed correctly, and that is already handled automatically. "A known problem or low reputation" can only be judged if members show each other a lasting identity, which costs every member their privacy.

What "the software honours the vote" can mean

Mechanism Works against a dishonest host? Works against modified member software?
The host's software removes a seat when shown a valid kick certificate No. The host can ignore it or cancel. Not relevant
Each member's software refuses to sign any tree that contains a seat named in a valid kick certificate Yes. A tree containing that seat cannot be completed while honest software is in it. No. Modified software can ignore certificates, but one honest member's refusal is enough to block the tree.

A kick certificate is a set of signed ballots from seated members that meets the lobby's published threshold. The second row is the real mechanism and it does satisfy the owner's wording: once a certificate exists, the software of every member, including those who voted against, will not sign with the kicked seat. Because every member must sign, this is effective.

The same property is the danger. A certificate obtained by fake seats makes every honest wallet refuse to sign with an honest member.

Recommended design

Use four tools, in this order of importance.

  1. Automatic removal for proven faults. A seat that misses a window or sends a bad partial signature is removed without any vote (B1). This covers the only misbehaviour that can actually be observed in a lobby.
  2. Host kick. The host may remove any seat before signing, with a reason code shown to the removed member. The host has the evidence (connection history, deposit, its own records) and bears the cost of failed rounds. Prior work already planned factory-kick-joiner.
  3. Personal block list. Each member's wallet holds a list of keys it will never sign with, and a list of hosts it will not join. If a blocked key is in the roster, the wallet says so and leaves. This needs no vote and cannot be abused against anyone else. It is the individual form of vote-kick.
  4. Kick certificate, optional and later. Only in lobbies where seats cost something (a deposit, a proof of coin ownership, or an invitation), with these safeguards:
  5. Threshold of two thirds of eligible seats, and at least five ballots.
  6. Only seats that have met the lobby's admission cost may vote.
  7. A reason code is required.
  8. Each seat may start one kick per lobby.
  9. No kicks once the ready check has begun; from then on only automatic removal applies.
  10. The effect is limited to this lobby. It is never published and never becomes a ban elsewhere.
  11. The kicked member is shown the certificate.

Stated limits

  • In an open lobby with free seats, vote-kick should be switched off. The profile decides (B9).
  • A kicked person can return under a new key unless seats cost something.
  • A host that disagrees with a kick can cancel the lobby and open another.
  • Vote-kick is most meaningful in invitation-only lobbies among people who know each other, where identities are real and the problem of fake seats does not arise.
B5. Deposits (question 5)

A deposit here has one job: to make a seat cost something, so that stalling is not free. It protects time, not money, and should be small.

Points that matter

A held payment cannot be made trustless. There are two ways to build it. If the host knows the secret, the host can take the deposit whenever it likes. If only the member knows the secret, the host can never take it, so it punishes nobody. RoboSats uses the first form and trusts its coordinator. The first form is acceptable only because the amount is small and the host has far more to lose (its vouch, its record, its business).

A held payment must be short. Holding a payment for the hours or days a lobby is open would lock routing nodes' funds, would be refused by consumer wallets, and risks channel closures near expiry. The deposit should therefore be taken at the ready check and released within minutes: when the member's valid partial signature arrives, or when the attempt ends through no fault of the member. The ten-minute signing budget in B1 is chosen for this. Taking the deposit at the ready check also makes the ready check mean something.

The wallet caps the deposit. The member's limits include a maximum deposit amount and a maximum hold time. A lobby that asks for more is not offered.

A wrongful forfeit for stalling cannot be disproved. A host can claim a member stalled and keep the deposit. Silence is not provable either way (B7). The member's remedy is to record it locally and avoid that host.

Members with no funds cannot pay any monetary deposit. This is the main audience for a factory wallet. A lobby that requires a deposit from everyone excludes them. The recommended answer is a mixed lobby:

  • Seats are either backed (deposit, coin proof, invitation or earned standing) or unbacked.
  • The host's rules cap the share of unbacked seats, for example one quarter. JoinMarket does the same with its 12.5% unbonded allowance.
  • Unbacked seats are the first to be replaced by standby seats after a failure.
  • The host accepts the remaining risk as a cost of acquiring new users, as ZmnSCPxj's notes expect the host to be "picky".

Recommendation. First version: no monetary deposit; invitations, the unbacked-seat cap, per-connection rate limits and the attempt cap. Second step: a held Lightning payment at the ready check for backed seats, using the hold operations the host's Lightning adapter already needs (DESIGN.md §14). Later: proof of coin ownership, and a privacy-preserving version if aut-ct matures.

B6. Reputation (question 6)

The governing fact

With free identities, a bad record is useless, because the owner discards the identity. Only two things work: a good record that took time to earn, and cost. Reputation for members should therefore be positive only. Reputation for hosts can be both, because a host's identity is anchored by its vouch and its capital and is costly to replace.

Stopping fake praise and fake blame

  • No free-form ratings. Stars and comments from arbitrary keys are trivially faked in both directions and no Nostr standard exists for them.
  • Fake blame is prevented by accepting only evidence that verifies by itself. A statement "member X stalled" or "host Y is a scammer" carries no weight in the software.
  • Fake praise for members is limited by treating a receipt as worth only as much as the host that issued it. A host decides which other hosts' receipts it accepts. A dishonest host can issue receipts to its own puppets, but an accepting host can ignore unknown issuers.
  • Fake praise for hosts is limited by counting only factories that exist on chain, which cost real capital to create.
  • Web-of-trust scores may be shown to the user as a hint, never used by the software to make a decision, because of the weaknesses in A8.

Privacy cost

  • Any lasting member identity lets a host link a person across factories. Receipts are therefore held by the member and shown only when the member chooses, and seat keys are new for each lobby by default.
  • Member reputation should never be published. A public record of which keys joined which host's factories is a map of the host's customers.
  • A host that publishes its funding outputs to build a record lets chain observers follow its factories. That is the host's choice.
  • Published fault proofs reveal an unsigned tree and the seat keys in it. Since the tree was never funded, the loss is small.
B7. Identifying the culprit (question 7)

What is achievable

Fault Identifiable by the host? Provable to members and outsiders?
Invalid partial signature from a member Yes, by checking each one (BIP-327) Yes, with the measures below
Member silent Yes No, never
Host sends inconsistent data Members can detect by comparing Yes, two signed messages
Host silent or never funds Members see it Weakly (B6)

Measures to build in from the first version

These are cheap now, while the message formats are still being written, and expensive to add later.

  1. Every signing message is signed with the sender's seat key and names the lobby, the terms hash, the roster hash and the attempt number. BIP-327 notes that nonces and partial signatures can otherwise be fabricated by an accuser.
  2. A member signs its partial signature together with a hash of the complete nonce set it was given. Without this, a host could send one member a different nonce set, receive a partial signature that is correct for that set, and present it as invalid against the real set. With it, a fault proof must show a nonce set whose hash the accused signed, in which every nonce is signed by its owner.
  3. The host signs every message it sends, so that inconsistency is provable.
  4. A fault proof is then a bundle: the roster and keys, the transaction being signed, the signed nonces, and the accused member's signed partial signature. Anyone can recompute the check and see that it fails.
  5. Silence is handled locally and never published. The software removes the silent seat and restarts. It never issues a public accusation of stalling, because none could be verified. This is also the protection against fake blame.
  6. Members verify the final signatures themselves and do not rely on the host's statement that signing succeeded.
  7. Fresh nonces for every attempt, never stored, as BIP-327 requires and as DESIGN.md §13 already states.

Limit

BIP-327 is explicit that a dishonest collector can always make a round fail. The measures above stop the host from framing a member with a forged or mismatched partial signature. They cannot stop a host from pretending a member was silent. The design accepts this: the host is the party with most to lose from failed rounds, and members judge hosts by their own experience.

Trade-offs to be aware of

  • A listing is a claim, not a fact. Everything in it is the host's unverified word until the wallet fetches the terms directly and later checks the tree. The wallet must treat the listing as a hint for filtering only.
  • This reverses the earlier decision that no factory state goes on Nostr (A1). The earlier concerns were leaking the host's business and making attackers' scanning easier.   • Expiry is not enforced by relays. Wallets must check it themselves.
  • The existing vouch does not prove funds.   • Members' network addresses are visible to the host on a direct connection. Prior work recommended Tor by default for members; that recommendation still stands.
  • Kind number. Prior work proposed 38102 for a per-factory announcement. Whether that number is free of collisions was not checked.

B10. First version, later additions (question 10)

Build first

  1. Lobby listing on Nostr (addressable, expiring), next to the existing vouch.
  2. Direct join; terms fetched from the host and compared to the listing hash.
  3. Versioned, host-signed terms. The wallet accepts or leaves automatically according to the member's limits.
  4. Scheduled start, minimum, maximum, closing time, optional start when full.
  5. Ready check with a 60-second window.
  6. Signing with seat-signed messages and the nonce-set hash (B7). This is first-version work because it shapes the message formats.
  7. Automatic removal and restart, at most three attempts, standby seats.
  8. Host kick with reason code. Personal block list in the wallet.
  9. Admission without money: invitations, a cap on unbacked seats, rate limits per connection.
  10. Local-only history in the wallet and at the host.
  11. Two profiles: Safety and Standard.
  12. Funding deadline, and the wallet's check of the funding inputs.

All of this can be exercised in the simulator, including scripted stallers and bad signers.

Add second

  • Held Lightning deposit at the ready check, with the wallet's caps.
  • Preference ballots for open shared rules.

Add later, if measurement shows a need

  • Host-signed completion receipts as portable standing.
  • Publishable fault proofs.
  • Kick certificates (Circle profile first).
  • Proof of coin ownership as a seat backing; a privacy-preserving form.
